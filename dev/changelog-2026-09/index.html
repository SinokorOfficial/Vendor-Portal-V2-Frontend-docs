    2026-09 변경 이력¶

    새 배포 감지 — 상단 배너 + 견적 업로드 저장 차단 (Infra #49)¶

    • 계기: 2026-09-30 CrsEstUploadExl 에서 1,695행이 나뉘지 않고 한 번에 세 번 저장돼 240초 벽에 모두 걸렸다. 분할 저장(PR #230)이 배포된 지 하루 뒤였다. 배포 전부터 열려 있던 화면이 메모리에 올라온 옛 저장 코드를 그대로 쓴 것으로 본다. 그 화면은 서버에 새로 요청할 일이 없어 router 의 자가치유(healStaleChunk, 옛 청크 404 때만 동작)에도 걸리지 않는다.
    • 감지: 빌드마다 dist/version.json({ buildId })을 만들고 같은 값을 화면 코드에 import.meta.env.VITE_BUILD_ID 로 박는다(vite.config.ts). stores/appVersion.ts 의 check() 가 version.json 을 읽어 값이 다르면 hasNewVersion 을 세운다. App.vue 가 5분마다, 그리고 탭으로 돌아올 때 확인한다(셸 화면만, 로그인과 별도 창 팝업은 제외). dev 서버는 빌드 ID 가 비어 있어 확인하지 않는다.
    • 배너: 헤더 바로 아래 화면 폭 전체 띠(높이 36px, 파랑) — A new version is available. Please refresh the page. + [Refresh](e-btn color="normal-line", location.reload()). 닫기 버튼은 없다. 새로고침하면 새 빌드로 다시 떠 빌드 ID 가 같아지므로 저절로 사라진다. 배너가 떠 있는 동안 작업영역 높이를 36px 줄인다.
      • 자동 새로고침은 하지 않는다 — 그리드에 올린 엑셀이나 입력 중인 내용, 열려 있는 다른 탭의 작업이 날아간다.
    • 저장 차단(CrsEstUploadExl 만): 저장 직전에 한 번 더 확인하고, 새 버전이면 $message.warning(OK 로 닫는 메시지 창)으로 A new version is available. Please refresh the page and save again. 를 띄우고 저장하지 않는다. 5분 주기를 기다리지 않으려고 저장 시점에 확인한다. hasNewVersion 은 새로고침 전까지 유지되므로 OK 로 닫아도 저장할 때마다 다시 막힌다.
    • ⚠️이 장치는 다음 배포부터 효과가 있다. 이 코드가 없는 옛 탭은 여전히 아무 안내도 받지 못한다. 이번 배포로 새로 뜬 화면부터 그다음 배포를 감지한다.
    • 검증: store 테스트 5종(다른 ID → 감지, 같은 ID → 그대로, dev → 확인 안 함, 404·네트워크 실패 무시, 한 번 감지하면 재요청 없음) 포함 16/16 통과. vite build 결과 version.json 의 ID 와 번들에 박힌 ID 일치. 배너는 App.vue 블록을 잘라 붙인 하네스를 빌드본(vite preview)에서 Playwright 로 실측 — 36px, 전체 폭, 아이콘 폰트 로드, Refresh 클릭 동작, 페이지 에러 0. 로컬 빌드본(vite preview 4050 + 백엔드 9050, .100)의 dist/version.json 을 다른 값으로 바꿔 버전 불일치를 재현하고, 로그인한 셸에서 배너와 저장 차단을 사용자가 직접 확인했다. vue-tsc --noEmit exit 0, ESLint 0.
    • 재현법: vite build 후 dist/version.json 의 buildId 를 아무 값으로 바꾸고 vite preview → 로그인 → 다른 탭에 갔다가 돌아오면 배너가 뜬다(처음 화면을 열 때는 확인하지 않는다 — 방금 받은 화면은 최신이므로). dev 서버(vite)는 빌드 ID 가 비어 있어 재현되지 않는다. → 트러블슈팅 §34.

    nginx /api/v2SsoLink 임시 스텁 제거 (Infra #47)¶

    • 컷오버 후 브라우저 디스크에 캐시된 레거시 로그인 셸을 구제하던 임시 블록(PR #186)을 뺐다. 레거시 셸이 로그인 직후 부르는 이 경로에 {"v2Url":"/?v2=1"} + Clear-Site-Data: "cache" 를 돌려줘 로그인 루프를 풀어주던 것이다.
    • 제거 근거(운영 nginx 로그): 9/9~11 하루 9~23건 → 9/13~14 1~3건 → 9/16·18·20·23 각 1건 → 9/24~29 6일 연속 0건. #47 의 판정 기준("연속 며칠 0")을 충족했다.
    • ⚠️그래도 캐시가 남은 사용자가 오면: 이 경로가 백엔드로 넘어가 500(NoHandlerFoundException)이 되고, 그 사용자는 로그인 화면 루프에 갇힌다. 5xx 알림에 /api/v2SsoLink 가 보이면 이것이다. 안내는 강력 새로고침(Ctrl+F5) 또는 캐시 삭제. 다시 늘면 이 블록을 되살리면 된다(git show 로 PR #186 참조).

    탭 간 세션 동기화 — 다른 계정 로그인 감지 (PR #220, BE #174, Infra #51)¶

    • SINOKORSESSION 은 탭이 아니라 브라우저 단위 쿠키다. 같은 브라우저에서 다른 계정으로 로그인하면 먼저 열려 있던 탭의 서버 세션까지 덮어써지는데, 그 탭의 Pinia 스토어(activeCompany/activeCustCd)는 옛 계정 값을 그대로 들고 있어 봉투가 남의 데이터에 닿는다. 운영에서 실제로 86건 발생(선사별로 나뉜 두 계정을 번갈아 쓰는 업무 관행).

    • ★다운로드·PDF 뷰어는 별도 axios 인스턴스(axios.create())라 요청 인터셉터를 안 탄다 — 첫 커밋에서 헤더가 빠졌고, 둘이 공유하는 fileDownOptions 에서 직접 붙여 해결했다. 이 파일에 axios 호출을 새로 추가할 땐 인터셉터를 타는지 확인할 것.
    • ★미결 Promise 경로가 셋이 됐다 — 날짜 가드(요청) · data.unknown(응답) · 세션 신원 불일치(응답).

    • 헤더는 선택적이다(없으면 서버가 검사하지 않음). 필수화하면 배포할 때마다 열려 있던 모든 탭이 409 를 맞는다. 남는 구멍은 '캐시된 옛 번들' 하나이고 새로고침하면 닫힌다.
    • 검증: 실제 브라우저(Playwright, 한 컨텍스트 탭 2개)로 헤더 전송 · 자동 새로고침 수렴 · 409 안내 노출(반복 새로고침 없음) 확인.

    CmsAzureLog '엔드포인트' 탭 — 지정한 API 가 실제로 나가는지 확인 (PR #162·#163, 백엔드 #114)¶

    • 왜 — 메일 발송 복구(PR #160) 이후 "V2 에서 나간 메일"을 확인할 방법이 없었다. TB_CMS_EMAIL 에는 출처 컬럼이 없고 V2·레거시가 같은 서비스에서 같은 프로시저(PKG_CM_EMAIL.SP_SET_EMAIL)를 호출하므로 메일 로그 화면으로는 두 포털을 영원히 못 가린다. 반면 V2 백엔드의 sendMail 200 응답 1건 = V2 발송 1건으로 1:1 대응한다(행은 Graph 발송 성공 뒤에만 쓰이므로).
    • 무엇 — URL 조각(예: sendMail)을 넣으면 상단 공통 기간 안에서 ① 상태코드별 건수·평균/p95 소요·최근시각 ② 최근 50건의 시각·상태·화면·클라이언트 IP 를 보여준다. 기존 '실패 요청 TOP' 은 Success == false 만 세므로 성공 건수를 볼 수 없다 — 이 탭이 그 빈자리를 채운다.
    • ★두 소스를 조인하지 않고 나눠 쓴다 — 집계는 App Insights AppRequests(구조화 필드), 최근 목록은 nginx 액세스로그다. AppRequests 에는 Referer 필드가 아예 없고 ClientIP 가 0.0.0.0(프록시 뒤)이라 "어느 화면에서 눌렀나 / 누가 눌렀나"를 알 수 없다(실측). 반대로 nginx 로그엔 소요시간이 없다. 그래서 소요는 집계 그리드에 평균/p95 로만 싣는다. 두 그리드의 건수는 어긋날 수 있다(집계=기간 전체, 목록=최근 50건 컷).
    • 그리드는 조회 전에도 그려둔다(후속) — 컬럼이 고정이므로 빈 상태 안내문 대신 헤더를 먼저 노출한다. 같은 이유로 '의존성 · 이벤트' 탭의 실패 상세 그리드(행 선택 전 안내문)도 상시 렌더로 바꿨다 — 이 탭의 나머지 4개 그리드는 원래 상시 렌더라 이제 5개가 일관된다. 부수효과로 그리드가 상시 마운트라 mounted() 어댑터가 그대로 유효해져, 초기 구현의 "api 준비까지 폴링 후 어댑터 재생성" 우회가 에러→성공 전환 때만 필요해졌다. ★그 폴링은 유한해야 한다 — 부분 실패(SUMMARY_ERROR 만 세팅)면 그 그리드는 계속 없는 상태라, 두 그리드를 함께 기다리던 초기 구현의 setTimeout 은 영영 돈다(초기 구현 결함, 함께 수정). 재시도 상한 20회·그리드별 독립 처리로 바꿨다.
    • 함정 — 기간을 바꿔 재조회하면 이 탭도 같은 기간으로 자동 재조회한다(안 하면 좌측만 새 기간이라 오독).
    • 조건은 탭 안이 아니라 상단 검색영역에 둔다(후속) — 처음엔 탭 안에 자체 검색바(입력 + 조회 버튼)를 뒀는데, 화면에 조회 트리거가 둘이 되어 어느 쪽이 무엇을 새로 고치는지 알기 어려웠다. 'URL 포함' 입력을 기간과 같은 줄에 <th>/<td> 쌍으로 붙이고(다른 화면의 col 라벨/입력 쌍 반복 관례 동일) activeTab === 'endpoint' 일 때만 노출한다 — 별도 행을 쓰면 검색영역이 두 줄이 되어 그리드 높이를 깎는데, 기간 우측은 비어 있다. ★.e-table 은 table-layout: fixed(global.scss)라 colgroup 이 절대적이고 내용이 칸을 넓히지 못한다 — 기간 칸을 */auto 로 두면 뒤 칸이 남은 폭을 다 가져가 0px 로 붕괴한다(실측: td 0px·셀렉트 30px). 그래서 기간 칸 폭을 상태별로 명시한다(탭 아님 * / 프리셋 210px / 직접지정 480px). ★같은 이유로 종전 .w200 래퍼는 정의가 없는 클래스였는데 칸이 넓을 땐 위젯이 셀을 100% 채워 우연히 멀쩡해 보였다 → .obs-range__win(200px) 신설. width prop 은 dx-text-box 엔 먹지만 dx-select-box 프록시엔 전달되지 않는다. 탭 안 버튼은 제거하고 상단 SEARCH 하나가 대시보드와 엔드포인트를 함께 조회한다(조각이 비어 있으면 조용히 건너뛴다 — 다른 탭에서 SEARCH 할 때 경고가 뜨면 안 된다). ★활성 탭은 e-card-tab 의 @change(탭 이름)로 받는데 클릭할 때만 emit 된다 — 초기값을 'overview' 로 직접 넣어야 한다. ★dx-text-box 는 폭 유틸(w200) 래퍼로는 안 잡혀 td 전체로 늘어난다 → 컴포넌트 width 옵션으로 지정.
    • 검증(실측) — 로컬에서 운영 워크스페이스를 향해 조회: sendMail → 200 4건(평균 550ms·p95 753ms), 목록에 화면(/tes/TesLashingExpn)·실 IP 정상 표시. 로컬은 azure.monitor.* 4개가 비어 있어 기본적으로 "설정 없음" 이 뜬다 — AZURE_MONITOR_* env 를 넣으면 DefaultAzureCredential 이 az CLI 로그인으로 떨어져 로컬에서도 조회된다.

    메일 팝업 필수입력 경고가 "undefined 은 필수..." 로 뜨던 문제 (PR #161)¶

    • CmsEmailPopup 검증 3곳(Subject/From/To)이 MSG000402 를 쓰는데 이 문구의 자리표시자는 {1} 이다. StringUtil.format 은 0-based 라 {0} 만 치환 — {1} 이 undefined 로 남아 "undefined 은 필수 입력 항목입니다." 가 출력됐다.

    메일 전송이 V2 에서 한 번도 동작하지 않던 결함 (PR #160)¶

    • 증상 — 메일 전송 시 "네트워크 문제로 저장/업로드가 중단되었습니다. 다시 시도해 주세요. [20260901|40]". 서버는 MultipartException → InvalidContentTypeException: ... content type header is application/json; charset=UTF-8. 꼬리의 [20260901|40] 은 TB_CMS_ERROR_LOG 의 ERR_DT|ERR_SN = 그날 40번째 에러다.
    • 원인은 헤더가 아니라 본문 파괴 — 백엔드 sendMail 은 @RequestPart("MAIN") 로 multipart 필수인데, axios 인스턴스 기본 헤더가 application/json 이라 axios 1.x 가 FormData 를 JSON 으로 치환한다(defaults/index.js: isFormData && hasJSONContentType → JSON.stringify(formDataToJSON(data))). Blob 파트가 {} 로 붕괴해 와이어에 {"MAIN":{}} 가 나간다 — 운영 에러로그의 PAYLOAD 와 정확히 일치. 즉 서버가 받아줬어도 메일 내용이 이미 없다.
    • ★V2 에서 성공한 적이 없다 — 기본 헤더도, $axios.post(url, formData) 호출부도 git log -S 결과가 최초 커밋 1건뿐이다. 레거시는 코드가 같았지만 axios 0.21.4 라 FormData 를 건드리지 않아 우연히 동작했다. 0.x→1.x 메이저 업그레이드로 인한 마이그레이션 회귀다. 화면에 성공으로 보일 여지도 없었다 — unknown=true 응답이 영구 pending Promise 를 반환해 MSG000399("E-mail sending is completed.") 토스트가 한 번도 뜬 적이 없다.
    • 수정 — ① util/http/index.ts request 인터셉터에 FormData 가드(cfg.headers.setContentType(undefined)) 추가 — 인터셉터는 transformRequest 보다 먼저 실행되므로 여기서 벗겨야 본문이 산다. ② CmsEmailPopup:278·FdsOrdMgt:1228 을 $axios.multipart 로 — 나머지 multipart 호출 17곳은 이미 이 헬퍼를 쓴다(규약 일원화). ③ 회귀 테스트 신설 — 가드 없으면 expected '{"MAIN":{}}' to be an instance of FormData 로 정확히 이 장애를 재현하며 실패한다(red/green 확인).
    • 검증(실측) — 브라우저에서 요청을 가로채 확인: 수정 전 application/json; charset=UTF-8 + body {"MAIN":{}} → 수정 후 multipart/form-data; boundary=----WebKitFormBoundary… + MAIN 파트(Content-Type: application/json) 정상. 기존 .multipart 경로와 일반 JSON 경로는 무변화(3경로 대조). 메일이 실제 발송되지 않도록 요청은 중단시켰다.
    • 동일 계열 전수조사 — 백엔드 multipart 엔드포인트 5개 중 불일치는 sendMail 1건뿐(나머지 uploadFile·vms/uploadExcel·excelExrateUpload 는 정상, extractGpt 는 死코드). 역방향 불일치 1건 발견 — /api/vendor/comm/uploadExcel 은 @RequestBody(JSON)인데 CFS 4화면이 FormData 를 보낸다(415). 다만 그 엔드포인트는 빈 DMap 만 돌려주는 스텁이고 레거시부터 死 라 이번 범위 밖.
