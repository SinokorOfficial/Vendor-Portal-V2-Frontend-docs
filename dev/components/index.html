    공통 컴포넌트¶

    자동 등록 (unplugin-vue-components)¶

    import 없이 템플릿에서 바로 쓰는 컴포넌트는 unplugin-vue-components 가 자동 등록합니다 (vite.config.ts).

    Components({
  dirs: [ 'src/components/auto/app', 'src/components/manual' ],
  extensions: [ 'vue' ],
  dts: 'src/components.d.ts',     // 등록명 타입 자동 생성(권위 있는 목록)
  directoryAsNamespace: true,     // 하위 폴더명을 컴포넌트명 접두로
  collapseSamePrefixes: true      // ECard + Grid → ECardGrid (중복 접두 제거)
})
    • src/components/auto/app/ECard/Grid/index.vue → 등록명 ECardGrid → 태그 <e-card-grid>
    • src/components/auto/app/EBtn/index.vue → EBtn → <e-btn>
    • src/components/manual/app/EHeader/index.vue → EHeader → <e-header>

    전체 목록은 자동 생성

    등록된 모든 컴포넌트와 정확한 태그명은 자동 추출 레퍼런스 › 공통 컴포넌트에 있습니다(빌드 시 src/components.d.ts 기준으로 갱신).

    두 디렉터리¶

    디렉터리 성격 예
    src/components/auto/app 화면에서 조립하는 공통 e-* UI EContentLayout, ECardGrid, EDateBox, ECodeBox, EBtn, EFileUploader
    src/components/manual 앱 셸·그리드 렌더러·도메인 컴포넌트 AppEHeader, AppESideMenu, AgGridVue* 렌더러/에디터, DashboardKbel*, Login

    검색 영역 입력값 양끝 공백 제거 (<e-search-area>)¶

    검색 영역의 <dx-text-box>, <e-code-box> 는 입력값의 양끝 공백을 제거해 v-model 에 싣는다. 가운데 공백은 그대로, 문자열이 아닌 값(숫자, null)도 그대로다.

    • 검색 영역 표시: EContentLayout, EDialogLayout 이 #search 슬롯을 <e-search-area> 로 감싸 provide(SEARCH_AREA_KEY, true) 한다. 슬롯 내용 컴포넌트의 부모 인스턴스는 슬롯을 그리는 쪽이라 #search 안에만 전달된다. 화면에서 따로 할 일은 없다.
    • 받는 쪽: DxTextBoxProxy 는 parseValue(값 경로, upper-case 와 같은 자리)에서, ECodeBox 는 값 변경과 Enter/F2 코드 조회어, 팝업 조회어에서 자른다. Enter 로 바로 조회해도 on-enter-key 핸들러가 보는 v-model 은 이미 잘린 값이다.
    • 검색 영역 밖(#content 의 입력 폼, 그리드 셀 에디터, $dialog 로 띄운 팝업의 입력 폼)은 기본값 false 라 동작 변경이 없다.
    • #search 슬롯을 쓰지 않는 검색창은 직접 감싼다(예: MdmNotice).
    <e-search-area>
    <dx-text-box v-model="search.SEARCH_KEYWORD" :on-enter-key="fnSearch"/>
</e-search-area>
    • 주의: :on-value-changed 콜백의 e.value 는 위젯 원본값이라 잘리지 않는다. 조회 파라미터는 v-model 값을 쓸 것.
    • 테스트: src/components/auto/app/ESearchArea/__tests__/searchAreaTrim.spec.ts

    <e-attach-file-grid> — 첨부 표준¶

    첨부 UI 는 이 컴포넌트로 일원화한다. 변형은 전부 props/이벤트로 처리하고, 화면에서 그리드를 다시 짜지 않는다.

    props 뜻
    mngt-no 파일 그룹 키. 값이 바뀌면 자동 조회하고, 비면 서버 호출 없이 목록만 비운다
    list-param 조회 param 오버라이드. CRS 는 DOC_TYPE:'RP' + COMP_CD 가 필수 — 백엔드가 이 둘로 레거시 SKR_DOC_MST UNION 쿼리로 분기한다
    upload-param 업로드 추가 param(기본 FILE_EXPL/MNGT_NO/CORP_CD/CUST_CD/COMP_CD 에 병합)
    allowed-ext / upload-viewable-only 업로드 확장자 제한. 후자는 뷰어 허용목록(공통코드 FILE_EXT)과 같게 묶는다
    (크기 제한) prop 없음. 50MB 고정(운영 nginx client_max_body_size) — 아래 참고
    staging 선택/드롭한 파일을 서버로 보내지 않고 @files-added 로 넘긴다. 모아뒀다 일괄 전송하는 화면용
    multi-select 체크박스 다중선택 + 다건 삭제(/api/file/deleteFiles 1회 호출). 기본은 단일선택
    readonly 조회 전용. 업로드·삭제 버튼과 드래그&드롭이 모두 꺼지고 다운로드·뷰어만 남는다
    can-upload / can-delete / viewer / auto-load / columns / title 노출·동작 제어
    이벤트 시점
    @uploaded 업로드 성공 후(목록 갱신은 컴포넌트가 이미 끝냄). 화면 후속 처리용
    @deleted 삭제 성공 후. 인자로 삭제된 행을 넘긴다
    @loaded 목록 조회 후
    @files-added staging 모드에서 파일이 선택/드롭됐을 때. 확장자 필터를 통과한 파일만 넘어온다

    다건 삭제 (multi-select)¶

    multi-select 를 켜면 체크박스 컬럼이 붙고, 삭제 버튼이 선택한 전부를 /api/file/deleteFiles 한 번에 보낸다. DB 는 WHERE FILE_SN IN (...) 한 방이라 트랜잭션 하나로 원자적이고, FTP 는 롤백이 불가능하므로 삭제하지 못한 항목을 응답으로 돌려준다(컴포넌트가 경고로 알린다).

    기본값이 false 인 이유는 켜는 순간 그 화면의 행 선택 방식이 바뀌기 때문이다. 첨부가 여러 건 붙는 화면(CmsFileUploadPopup)만 켜져 있다.

    업로드 사전검증 — 크기(50MB)와 개수(200장)¶

    상한이 둘이고 출처가 다르다.

    상한 정본 넘기면
    크기 50MB 운영 nginx client_max_body_size 50m(frontend/nginx.conf) nginx 가 413 을 HTML 로 끊는다
    개수 200장 Tomcat server.tomcat.max-part-count(백엔드 210) Spring 이 "용량 초과" 로 둔갑시킨다 ↓

    백엔드 spring.servlet.multipart 는 1000MB 지만 nginx 가 앞이라 실효값이 아니다.

    ★개수 초과가 "Maximum upload size exceeded" 로 뜬다. Tomcat 의 FileCountLimitExceededException 을 Spring 이 메시지의 count·limit·exceed 를 보고 MaxUploadSizeExceededException 으로 바꾸기 때문이다. 2026-10-16 에 FdsInvoice 가 7MB 로 7건 막혔는데 용량 문제가 아니었다(같은 기간 단일 파일 49.7MB 는 정상). 사용자가 압축하거나 화질을 낮춰도 안 풀리므로 프론트에서 먼저 막아 사유를 제대로 알린다.

    프론트 상한(200)은 서버(210)보다 항상 낮아야 한다 — 본문은 파일 N개 + param 1개 이고, 서버가 먼저 걸리면 사유를 알 수 없는 에러가 된다.

    컴포넌트가 보내기 전에 거르는 것:

    검증 동작 메시지
    파일 1건 > 50MB 그 파일만 제외하고 나머지는 업로드 MSG000432 (파일명 + 용량 나열)
    한 요청 합계 > 50MB 통째로 차단 MSG000433 (합계 용량)
    한 요청 개수 > 200 통째로 차단 MSG000447 (상한 + 선택 장수)

    합계까지 보는 이유는 FileService 가 선택한 파일 전부를 하나의 multipart 요청으로 묶기 때문이다(appendFile('files', file) × N → multipart() 1회). 개별이 다 통과해도 합계가 넘으면 그대로 413 이다.

    staging 모드에서는 파일 1건 검증만 돈다. 스테이징 화면(CrsFileUploadPopup)은 모아둔 파일을 1건씩 별도 요청으로 보내므로 합계가 상한에 걸리지 않는다.

    컴포넌트를 안 거치는 업로드도 막힌다. 상한·문구는 ~/util/service/uploadSize 한 곳에 있고(개수 검사는 크기보다 먼저 본다 — 장수가 많으면 합계도 같이 넘기 쉬운데 사용자가 손쓸 수 있는 건 개수 쪽이다), 최종 검증은 http.multipart 가 한다. 파일이 실리는 요청은 예외 없이 그 함수를 지나므로 — FileService 경유(첨부·매뉴얼)든 화면이 $axios.multipart 를 직접 부르는 경로(엑셀 업로드·환율·메일)든 — 한 곳으로 전부 덮인다. 호출부가 전부 .catch(error => this.$message.error(error.message)) 라 문구가 그대로 뜬다.

    둘의 차이는 초과분 처리뿐이다. 컴포넌트는 파일을 고르는 시점이라 초과분만 빼고 나머지는 올리고, http.multipart 는 FormData 가 이미 만들어진 뒤라 통째로 막는다. 합계는 JSON 파트(appendJson 의 Blob)까지 더한다 — nginx 는 파트를 가리지 않고 본문 전체를 보기 때문이다.

    업로드 뒤 — 일부만 실패했을 때¶

    백엔드는 성공한 파일만 돌려준다(BE #225). 종전엔 한 장이라도 전송에 실패하면 전부 롤백됐는데, 그러면 이미 NAS 에 올라간 파일이 고아로 남았다. 지금은 파일마다 전송 후 짧은 트랜잭션으로 커밋하므로 성공분이 그대로 남는다.

    ⇒ 화면은 보낸 목록과 응답을 대조해 빠진 파일만 알려야 한다. 안 그러면 그리드에 행이 덜 붙은 채 성공처럼 보인다.

    const missing = notUploadedNames( files, result && result.data )
if ( missing.length ) this.$message.warning( notUploadedMessage( missing ) )   // MSG000448

    ★notUploadedNames 는 개수로 상계한다(Set 이 아니라). 같은 이름의 파일을 여러 장 고를 수 있다.

    전부 실패하면 서버가 예외를 던지므로 .catch 로 간다 — 한 장만 보내는 화면은 종전과 동작이 같다.

    적용: e-attach-file-grid, CmsDocumentPopup(다건을 한 요청에 싣는 두 곳).

    루프로 올리는 화면은 동시 수를 묶는다¶

    CrsFileUploadPopup(수리사진 자동매칭)은 파일 한 장당 별도 요청이다. 종전엔 forEach 안에서 await 없이 쏴 파일 수만큼 요청이 한꺼번에 나갔다 — 업로드 1건은 FTP 연결 2개(제어 + passive 데이터)를 새로 열므로 50장이면 순간 100개다.

    2026-10-19 운영 실측: 30초에 81건이 몰려 전송이 0.6초 → 1.3 → 3.8초로 밀리다 한 장이 16.6초에 실패했다(설정 타임아웃 어느 것과도 안 맞는다 — NAS 가 끊은 것). 버스트가 끝나자 381ms 로 복귀했다.

    워커 4개가 큐를 나눠 쓴다(UPLOAD_CONCURRENCY). 장당 0.4초대를 유지하므로 전체 소요는 오히려 짧아진다.

    포탈 미러(SP_SET_FILE4PORTAL)는 파일 단위가 아니다

    skr_doc_mst 에서 그 mngt_no 행을 DELETE 하고(여기서 커밋) tb_cms_atfile 의 'RP' 첨부를 전량 다시 INSERT 한다. p_file_nm 은 로그에만 쓰인다.

    파일마다 부르면 ①같은 전량 재적재를 N 번 반복하고 ②DELETE 와 INSERT 사이 커밋 때문에 동시 호출이 겹치면 한쪽이 비운 사이 다른 쪽이 INSERT 해 미러가 어긋나며 ③업로드 도중에 부르면 그 시점까지 올라간 파일만 실린다. 종전엔 셋 다 하고 있었다.

    ⇒ 업로드를 전부 끝낸 뒤, 성공분의 ESTIMATE_NO 를 distinct 해 견적당 한 번만 부른다.

    ℹ️견적이 여러 개여도 전부 올라간 뒤에 견적 수만큼 호출한다(견적별로 끝나는 대로 부르지 않는다). 견적별 즉시 호출은 잔여 장수를 정확히 세야 하고, 틀리면 ③이 그대로 재현된다. 대신 업로드 도중에 창을 닫으면 어느 견적도 미러되지 않는다(파일은 DB 에 있다). 2026-10-19 기준 현행 유지하고 관찰 중 — 큰 배치에서 민원이 생기면 견적별 즉시로 바꾼다.

    ★로컬은 nginx 를 거치지 않는다(4050 vite 프록시 → 백엔드 직결). 이 사전검증이 없으면 로컬에서만 되는 업로드가 생기고, 운영에서는 nginx 가 413 을 HTML 로 돌려줘 화면에 정상 문구조차 못 띄운다.

    크기 표기는 올림이다. 반올림하면 상한을 1바이트 넘긴 파일이 50.0 MB 로 찍혀 "50MB인데 왜 안 되냐"가 된다 — 거절 사유로 보여주는 숫자는 상한 이하로 보이면 안 된다.

    사전(TB_CMS_DATA_DIC)에 코드가 없으면 $lang 이 코드 문자열을 그대로 돌려주므로, 등록 전 배포에서 MSG000432 가 화면에 노출되지 않도록 영문 기본 문구로 폴백한다(langOr).

    조회 전용 (readonly)¶

    첨부를 보기만 하는 화면(예: CrsEstApproval — 첨부 추가/삭제는 CrsEstimate 에서만 한다)은 readonly 로 쓴다. 업로드 버튼·삭제 버튼·<input type=file> 이 사라지고 onDrop 도 막히며, 다운로드·뷰어 컬럼만 남는다.

    <e-attach-file-grid
    readonly
    :mngt-no="main.ESTIMATE_NO || ''"
    :list-param="fileListParam"
/>

    업로드가 막힌 상태(readonly 또는 can-upload="false")에서는 드롭존 워터마크(구름 아이콘)도 감춘다. 드롭을 권하는 그림인데 실제로는 아무 일도 일어나지 않아 사용자를 헷갈리게 하기 때문이다. CrsEstimate 처럼 조건부로 막는 화면에서는 올릴 수 있게 된 순간 구름이 나타나 상태 표시 역할도 한다.

    스테이징 모드¶

    첨부 목록이 아니라 올리기 전 파일 목록을 다루는 화면(예: CrsFileUploadPopup 의 견적서 일괄 매칭 업로드)은 staging 으로 쓴다. 서버 조회·업로드·삭제를 끄고 드롭존·워터마크·확장자 검증·총건수만 재사용한다.

    <e-attach-file-grid
    ref="attachGrid"
    staging
    :auto-load="false"     <!-- 서버 조회 안 함 -->
    :can-delete="false"    <!-- 삭제 판단은 화면 몫 -->
    :columns="fileColumns"
    upload-viewable-only
    @files-added="fnAttachFiles"
>
    <template #actions>
        <e-grid-btn button-type="delete" @click.stop="fnDeleteRow"/>
    </template>
</e-attach-file-grid>

    행 조작은 this.$refs.attachGrid.getAdapter() 로 직접 한다. 총건수(:total)와 워터마크는 어댑터의 getRowCount() 를 읽는 반응형이라 화면이 행을 직접 넣어도 맞는다.

    뷰어 판정의 정본은 공통코드 TB_CMS_CD_DTL / MSTR_CD='FILE_EXT'(화이트리스트) 다. 컴포넌트가 /api/code/selectCommonCode 로 모듈 단위 1회만 조회해 공유한다. 허용목록 밖이면 MSG000400 경고, PDF 는 openPdfViewer, 나머지(이미지·ZIP)는 캐러셀 새 창(CmsImageCarouselPopup)으로 연다. 확장자를 늘리려면 코드가 아니라 공통코드를 고친다.

    화면이 직접 파일을 고를 때 — FileService.select()¶

    첨부가 아니라 엑셀 업로드·템플릿 교체처럼 한 건짜리 업로드는 공통 컴포넌트를 쓰지 않는다. 이때 화면 템플릿에 <input type="file"> 을 두지 않는다.

    import { FileService } from '~/util'

async fnExcelUpload () {
    const file = await FileService.select()          // 고르지 않고 닫으면 null
    if ( !file ) return
    const form = new FormBuilder().append( 'file', file ).append( 'type', 'ESTIMATE' ).build()
    this.$axios.multipart( '/api/vms/comm/uploadExcel', form )...
}

    select() 는 DOM 에 붙이지 않은 <input> 을 그 자리에서 만들어 .click() 하고, 선택이 끝나면 버린다. 확장자를 제한하려면 인자로 넘긴다 — FileService.select( 'application/vnd.ms-excel,...' ).

    왜 숨은 input 을 두지 않나¶

    종전엔 화면마다 display:none 인 input 을 심어두고 버튼이 $refs.xxx.click() 으로 선택창을 열었다. 그 input 이 DOM 에 남아 두 가지를 낳았다.

    1. 밖에서 때릴 수 있다 — el.files 를 꽂고 dispatchEvent(new Event('input')) 을 쏘면 핸들러가 돈다. 버튼을 v-show 로 가려도 input 은 그대로라 소용이 없다
    2. 엉뚱한 input 이 잡힌다 — document.querySelector('input[type=file]') 는 DOM 에서 먼저 나온 것을 집는다

    실제로 CrsEstUploadExl 에서 협력사 계정이 업무 엑셀을 올리려다 관리자 전용 템플릿 업로드로 빠지는 일이 12회 났다(2026-09~10). 그 화면은 관리자 전용 input 이 업무용보다 앞에 있었다.

    select() 로 바꾸면 핸들러가 DOM 리스너가 아니라 클로저라 밖에서 부를 수 없고, 집을 요소도 없다. 2026-10 기준 src/pages 에 숨은 file input 은 0개다(<e-attach-file-grid> 의 것만 남아 있고 그건 드롭존에 실제 요소가 필요하다).

    권한 구분은 메서드로 한다¶

    업무용과 관리자 전용을 DOM 요소가 아니라 호출 경로로 가른다.

    업무용 관리자 전용
    메서드 fnExcelUpload() fnUploadTemplate()
    버튼 메뉴 버튼 v-if="isAdmin"
    API /api/vms/comm/uploadExcel /api/file/uploadFile + TYPE:'FORM'

    클라이언트 구분은 오발 방지이지 보안이 아니다. 권한의 관문은 서버의 isAdminRole() 이다.

    ⚠️select() 는 브라우저 정책상 사용자 제스처(클릭) 안에서 호출해야 선택창이 열린다. 버튼 핸들러에서 바로 부르면 되고, await 뒤에서 부르면 막힌다.

    ⚠️v-show 로 되돌리지 말 것. CSS 로 가릴 뿐 DOM 에 남는다.
