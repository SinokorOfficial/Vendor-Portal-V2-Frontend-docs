    2026-11 변경 이력¶

    파일 정합성 화면: 파일 상태 8분류와 [동기화] 버튼 (PR #357, Infra #107)¶

    첨부 파일 하나를 실물(NAS), TB_CMS_ATFILE, SKR_DOC_MST(V2 가 넣은 /VENDOR 행) 세 곳에 있느냐로 8분류해 보여 주고, [동기화] 버튼으로 규칙대로 맞춘다. 규칙 정본은 Infra #107 본문(2026-11-09 사용자 결정).

    • 구분 열이 "5. 실물 없음, 둘 다" 처럼 규칙 번호와 이름으로 바뀌었다. 처리 열(SKR_DOC_MST 등록, ATFILE 추가, 둘 다 삭제, ATFILE 삭제, SKR_DOC_MST 삭제, 처리 없음)을 더했다.
    • 검색 영역에 "처리 규칙" 툴팁을 넣었다. 8분류와 처리가 그대로 들어 있어 나중에 규칙을 잊어도 여기서 본다(rules.js 한 곳에서 만든다).
    • [포탈 재등록] 버튼을 [동기화] 로 바꿨다. 누르면 팝업에 규칙표, 처리 대상 미리보기(엑셀 내려받기), 폴더 단위 경고, 삭제 상한 초과 안내가 뜨고, [동기화 실행] 을 한 번 더 확인한 뒤 서버가 처리한다. 결과(처리됨, 건너뜀 사유, 실패)는 같은 그리드에 보여 준다.
    • [MISSING 삭제문 생성] 버튼과 SQL 다이얼로그를 지웠다. 5, 6번은 이제 [동기화] 가 지운다.
    • 검색 옵션 "포탈시스템 포함", "포탈 미등록 점검" 을 지웠다. SKR_DOC_MST 는 늘 같이 분류한다. "미등록 파일(고아) 점검" 은 "4번(실물만)도 찾기" 로 이름을 바꿨다.

    재고 현황 집계가 조회마다 쌓이던 것, EIR 붙여넣기가 LF 줄바꿈을 못 나누던 것 (PR #353, Infra #98)¶

    재고 현황(MvsStockStatus) 타입별 집계 (Infra #98 1-8)¶

    • 증상: 조회를 두 번 누르면 위쪽 타입별 칸(22GP ~ 22TN)이 두 배가 됐다. TOTAL 은 조회마다 행 수로 다시 계산해 맞게 나와서, 타입별 칸의 합과 TOTAL 이 어긋나 보였다.
    • 원인: fnCalculateStock 이 this.C_22GP += 1 식으로 더하기만 하고 0으로 되돌리는 곳이 없었다.
    • 조치: fnSearch 가 그리드를 비울 때 fnClearStock 으로 타입별 칸 12개와 TOTAL 도 0으로 비운다. 조회가 실패해도 빈 그리드와 칸이 맞는다.
    • 테스트 src/pages/mvs/__tests__/stockStatusCount.spec.ts: 같은 결과로 두 번 조회, 결과가 바뀐 조회, 실패한 조회. 고치기 전 코드에서 3건 모두 실패하는 것을 확인했다.

    EIR 발급 화면 붙여넣기 줄 구분 (Infra #98 1-9)¶

    • 수입/수출 발급 화면(EirImportIssue, EirExportIssue)의 붙여넣기(parseTextToJson)가 줄을 \r\n 으로만 나눴다. 그래서 LF 만 쓴 텍스트를 붙여넣으면 여러 번호가 한 행으로 붙었다(공백 제거 때문에 A\nB 가 AB 한 건).
    • 이제 CRLF, LF, CR 을 모두 줄 구분으로 본다. 엑셀에서 복사한 CRLF 텍스트는 전과 같다.
    • 4-1(같은 달 PR #351 항목)에서 현재 동작으로 고정해 둔 테스트 기대값을 바꾸고, CR 만 쓴 경우와 CRLF, LF 가 섞인 경우를 더했다.

    EIR 수입/수출 발급 화면의 똑같은 메서드를 공통 파일로 (PR #351, Infra #98)¶

    Infra #98 4-1. 두 화면(EirImportIssue, EirExportIssue)은 각자의 페이지로 그대로 두고, 두 화면에 글자까지 같게 있던 메서드만 src/pages/eir/eirIssueCommon.js 로 옮겼다. 동작은 바뀌지 않는다.

    • 옮긴 것 8개
      • computed searchGridTotal
      • methods fnSend, fnGetSubmitErrorMessage, fnNormalizeBlNo, fnBlNoPrefix, fnIsValidBlNo, fnCheckClipboardData, parseTextToJson
    • 방식
      • 공통 파일의 function 을 두 화면의 methods 와 computed 에 같은 이름으로 등록한다. FdsOrdMgt 의 gridOptions.js 와 같은 방식이고 mixin 은 쓰지 않았다.
      • 화면 쪽 호출(this.fnNormalizeBlNo(...), 템플릿의 fnSend('S'), 붙여넣기의 fnCheckClipboardData() 등)은 그대로다. 본문의 this 도 기존처럼 화면 인스턴스다.
      • 본문은 그대로이고 들여쓰기만 바뀌었다. 공통 함수끼리도 원본처럼 this. 로 부른다.
      • fnCheckClipboardData 에서 수입 화면에만 있던 주석 처리 코드 3줄은 공통 파일에 주석으로 남겼다.
    • 화면에 남긴 것(두 화면에서 실제로 다르다)
      • fnSubmit: 응답 행 검사가 수출은 data && data.ERROR === 'Y', 수입은 data.ERROR === 'Y' 이다. 응답 RESULT 에 null 이 섞이면 수입은 예외로 빠져 재조회 안내가 뜨고, 수출은 그 행을 건너뛴다.
      • fnSearchValidation: 수입은 Search 그리드 행을 getItems()(변경분 캐시)로, 수출은 getRows()(그리드 전체 행)로 읽는다. 문구도 B/L No. 와 B/K No. 로 다르다.
      • fnGetSearchGridOptions: 머리글 키가 BLNO 와 BK_NO 로 다르고, 빨간 글씨 조건이 수입은 params.value 의 참거짓, 수출은 ObjectUtil.isEmpty(params.data.BK_NO) 이다.
      • fnSearch, fnReset, fnSendEIR, fnCancelEIR, fnSendValidation, fnCancelValidation, 화면별 그리드 옵션은 원래부터 다르다.
    • 공통 프로시저 허용 목록(Infra #92): 각 화면 dataset.js 의 프로시저 리터럴은 그대로이고 공통 파일에는 없다. 허용 목록 생성 결과가 전후로 같다.

    테스트를 134건 추가했다(전체 298 → 432, src/pages/eir/__tests__/eirIssueCommon.spec.ts). 옮기기 전 원래 화면 코드에서 먼저 통과시켰고, 두 화면의 methods 를 같은 기대값으로 돌린다.

    • B/L 번호 정규화(공백, 탭, 줄바꿈, 전각 공백, 소문자, 빈 값, null), 선사별 접두어(SNKO, HALK, HSLI, 빈 값), 16자와 접두어 판정
    • 엑셀 붙여넣기 텍스트(여러 행, 여러 열, 가운데 빈 행, LF 만 쓴 텍스트는 한 행으로 붙는 현재 동작, 빈 텍스트)
    • 전송 응답을 못 받았을 때의 재조회 안내 문구
    • fnSend 의 확인창, 검사에서 막힘, 아니오, 재진입 차단, 예외 뒤 플래그 해제
    • 클립보드 붙여넣기(정상, 빈 값, API 없음, 읽기 실패), Search 그리드 행 수
    • 두 화면이 공통 파일의 같은 함수를 등록하는지(한쪽에 복사본이 다시 생기면 걸린다)

    승인 조회도 개선본 프로시저를 쓴다 (PR #354)¶

    Infra #115. CrsEstApproval 의 조회를 SP_GET_EST → SP_GET_EST_NEW 로 바꾼다. 견적 조회 화면은 PR #350 에서 이미 넘어갔으므로, 이로써 SP_GET_EST 는 호출처가 없다.

    • 결과는 같다. .100 에서 선사 3개의 승인 조회를 전체 컬럼 양방향 MINUS 로 대조해 0행을 확인했다(SNKO/PUS12 14,726행, HALK/PUS01 11,184행, HSLI/INC07 1,795행).
    • 파라미터 이름과 순서가 SP_GET_EST 와 같다. 관문이 ALL_ARGUMENTS 를 이름으로 읽어 꽂으므로 화면에서 더 보낼 값은 없다.
    • 속도 이득은 거의 없다. 이 화면은 하루 1~3명이 쓰고 20초를 넘긴 호출이 0건이다. 받는 것은 file_yn 을 exists 로 바꾼 분 정도다.
    • 바꾸는 이유는 성능이 아니라 정리다. 지금은 같은 데이터를 보는 두 화면이 서로 다른 프로시저를 본다. 하나로 모으면 다음에 로직을 고칠 때 어느 쪽을 고쳐야 하는지 헷갈리지 않는다.
    • SP_GET_EST 는 DB 에 그대로 둔다. 되돌릴 일이 생기면 이 파일 한 줄로 돌아간다.

    DB 쪽 선행 조건은 없다. 운영에 지금 컴파일돼 있는 SP_GET_EST_NEW 도 APP_YN='Y' 가지를 그대로 갖고 있어 이 화면이 바로 탄다. 승인 전용 커서로 갈라진 새 본문을 컴파일하면 그때부터 그쪽을 탄다.

    허용 목록은 112 에서 111 로 줄어든다. 두 화면이 같은 이름을 쓰게 되기 때문이다. 이번에는 이름이 빠지기만 하므로 갱신 버튼을 당장 누르지 않아도 조회가 막히지 않는다. 백엔드가 들고 있는 옛 목록이 상위집합이라 그렇다. 다만 다음 기동이나 03:00 에 자동으로 맞춰지니, 정리 삼아 눌러 두면 깔끔하다.

    사용자 관리의 회사 코드 팝업은 자기 모듈 회사만 보인다 (PR #348)¶

    Infra #91 "#88 처리 뒤 남은 항목" 중 "회사 코드 선택 팝업이 모듈로 거르지 않는다".

    • CmsUserMgt 의 회사 코드 팝업 두 곳(조회 조건, 상세의 소속 회사)에 늘 USER_ID(로그인 사용자)를 넘긴다. 종전에는 조회 조건만, 그것도 수리장 관리자(CRS00)일 때만 넘겼다.
    • 팝업 쿼리(selectCorp)는 이 값으로 ADMIN 에게는 전부, 그 밖에는 SYSTEM_DIV 가 내 역할 앞 3자인 회사만 돌려준다. 서버 저장 판정(법인 범위)과 같은 규칙이다.
    • 자기 모듈은 사용자 소속 회사의 모듈이 아니라 역할로 정해진다. 예: CRS00 담당자는 소속이 SNKO(FDS)지만 CRS 회사를 다룬다.
    • 종전에는 모듈 관리자가 범위 밖 회사를 고를 수 있었고, 저장 때 서버의 법인 범위 판정(백엔드 PR #223)이 거절했다. ADMIN 화면은 바뀌지 않는다.
    • 포트 그리드의 회사 칸은 서버 판정 대상이 아니라 그대로 둔다.

    비밀번호 초기화 화면에서 하는 일 없던 사전 확인 호출을 뺀다 (PR #346)¶

    Infra #91 판단 항목 "비밀번호 찾기". 백엔드 PR #292 와 짝이다.

    • src/pages/login/pw-init/index.vue: "Reset the Password" 가 /api/auth/find/password/user 를 먼저 부르고 나서 /api/auth/find/password 를 불렀다. 앞의 호출은 메일 발송이 주석 처리돼 하는 일이 없었고, 응답의 인증번호도 쓰지 않았다. 이제 /api/auth/find/password 만 부른다.
    • 백엔드는 그 API 를 지운다. 이 PR 이 먼저 배포돼야 한다.
    • 발송에 성공하면 같은 화면에서 다시 누를 수 없게 막는 동작은 그대로다. 종전과 달리 발송이 실패하면 다시 시도할 수 있다.

    메일 팝업의 From 칸을 숨긴다 (PR #347)¶

    Infra #91 판단 항목 "메일 발신자".

    • CmsEmailPopup(TES 4개 화면, FDS Invoice 에서 여는 메일 팝업)의 From 칸을 숨긴다(v-show="false", 템플릿에는 남겨 둔다). 값은 메일 양식 프로시저가 선사 공용 발신함(sendonly@…)으로 채우고, 보낼 때 그대로 넘긴다.
    • From 이 비었을 때 로그인 사용자 메일로 채우던 보정은 없앴다. 백엔드 PR #295 가 공용 발신함 말고는 거절하므로, 채워 봐야 서버에서 실패한다. 비어 있으면 From 필수 검사가 안내한다.
    • 서버 검사(백엔드 PR #295)가 실제 차단이고, 이 PR 은 화면을 그에 맞춘다. 배포 순서는 상관없다.

    문서: 비밀번호 찾기 안내와 "No endpoint" 응답 코드를 맞춘다 (PR #349)¶

    Infra #91 조치(백엔드 PR #292, #293) 뒤 문서에 남은 차이를 맞춘다.

    • 사용자 문서 시작하기에 비밀번호 찾기 안내를 더했다. 등록된 이메일과 정확히 같아야 임시 비밀번호를 받는다(주소 일부로는 안 된다). 여러 개 등록돼 있으면 그중 하나를 입력하고, 메일은 그 주소로 간다.
    • 개발 문서 문제 해결의 "No endpoint POST /api/…" 안내를 404 로 고쳤다. 2026-11-04 전에는 500 으로 나갔다.

    견적 조회가 개선본 프로시저를 쓴다 (PR #350)¶

    Infra #115. CrsEstimate 의 조회를 SP_GET_EST → SP_GET_EST_NEW 로 바꾼다.

    • 프로시저는 운영에 이미 컴파일돼 있다. 결과는 같다 — .100 에서 선사 3개(SNKO/HALK/HSLI) 체크섬을 원본과 대조했다.
    • 파라미터 이름과 순서가 SP_GET_EST 와 같다. 관문이 ALL_ARGUMENTS 를 이름으로 읽어 꽂으므로 화면에서 값을 더 보낼 것은 없다.
    • 개선분은 file_yn 을 count(UNION ALL) 에서 exists or exists 로 바꾼 것이다. 약 -12%. 평소 2.1초가 1.9초쯤 된다.
    • 승인 화면(CrsEstApproval)은 SP_GET_EST 를 그대로 쓴다. 한쪽만 바꿔 운영에서 비교하려는 것이고, 하루 1~3명이 쓰는 저빈도 화면이라 급하지 않다.

    배포 뒤 관리자 화면에서 허용 목록 갱신 버튼을 눌러야 한다(Infra #92). 목록은 빌드가 자동으로 만들지만 백엔드는 기동, 매일 03:00, 갱신 버튼 때만 다시 읽는다. 누르지 않으면 다음 03:00 까지 견적 조회가 거절된다.

    CI 의 Trivy 를 GitHub 릴리스에서 직접 받고, 실패해도 PR 을 막지 않게 한다 (PR #345)¶

    2026-11-03 밤부터 PR 의 CI(ci.yml) Trivy 단계가 설치에서 실패하게 됐다. 백엔드 PR 에서 먼저 드러났다(백엔드 #289).

    • trivy-action@v0.36.0 이 부르는 설치 단계(setup-trivy)는 Trivy 본체를 get.trivy.dev 에서 받는다. trivy.dev 도메인이 2026-11-03 21:34 UTC 에 등록업체 주차 페이지로 바뀌면서 이 주소가 DNS 에서 사라져 curl 이 exit 6 으로 죽는다(상류 이슈 aquasecurity/setup-trivy #42).
    • 캐시는 PR 마다 따로 저장돼 다른 PR 이 재사용하지 못한다. 그래서 새 PR 은 매번 본체를 새로 받는다.

    바꾼 것¶

    • Install Trivy 단계를 새로 넣었다. GitHub 릴리스에서 trivy_0.70.0_Linux-64bit.tar.gz 를 받아, 워크플로에 고정한 sha256 과 대조한 뒤 PATH 에 올린다. 버전은 trivy-action@v0.36.0 의 기본값과 같다. 다른 Trivy 단계처럼 빌드 성패와 무관하게 돈다(if: always()).
    • 취약점 스캔과 SBOM 단계에 skip-setup-trivy: 'true' 를 줘 위에서 설치한 본체를 쓴다.
    • Trivy 단계(설치, 스캔, SBOM)에 continue-on-error: true 를 붙였다. 원래 보고만 하는 단계라, 외부 장애로 스캔을 못 해도 PR 을 빨간불로 만들지 않는다. 실패는 그 단계 로그에 남고, 실행 요약에는 "결과 파일 없음" 이 나온다.
    • 문서: 빌드와 배포의 CI 절.

    레거시 SSO 진입(?ssoToken=) 처리 삭제 (PR #344)¶

    레거시 포탈이 /?ssoToken=<jwt> 로 보내면 부트스트랩이 /api/link 로 넘겨 비밀번호 없이 로그인시키던 분기를 지웠다(Infra #91 10). 레거시는 2026-10-23 종료됐고, 운영 진입은 9/8 컷오버 뒤로 0건이었다. 백엔드의 /api/link 와 SSO 로그인도 같은 날 지웠다(백엔드 PR #288).

    • src/plugins/bootstrap.ts: ssoToken 분기 삭제. 이제 이 쿼리는 무시되고 보통 진입처럼 세션을 확인한다(없으면 로그인 화면).
    • docs-dev/auth.md: SSO 유입 절을 폐쇄 기록으로 바꿨다.

    수리장 관리자 CRS00 — 사용자 관리에서 소속 회사 REPAIR 고정 (PR #343)¶

    수리장 관리자 역할 CRS00 이 사용자 관리(CmsUserMgt)만 쓰도록 화면을 맞췄다. 판정은 세션 역할에 CRS00 이 있고 ADMIN 이 아닐 때다(isRepairAdmin).

    • NEW 를 누르면 상세의 CORP 가 REPAIR 로 채워진다. 관리자가 팝업에서 REPAIR 를 고른 것과 같게 이름과 관계 회사 행(selectCorpRel)도 불러온다.
    • 상세 CORP 칸은 읽기 전용이다. 기존 사용자를 열었을 때도 바꿀 수 없다(돋보기 버튼도 함께 꺼진다).
    • 조회 조건 CORP 팝업은 SYSTEM_DIV 가 CRS 인 회사만 보인다. 기존 selectCorp 의 USER_ID 조건(세션 사용자 역할의 앞 3자)을 쓴다. 칸에 코드를 직접 입력해도 같은 범위에서만 찾는다.

    API 허용 역할과 회사 관리 차단은 백엔드 PR #284, 역할 행 등록은 사용자가 DB 에 했다. 역할이 없는 계정에는 아무 변화가 없다.
