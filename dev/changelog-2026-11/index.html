    2026-11 변경 이력¶

    IP 차단 관리 — 관찰 탭(지금 기준으로 걸리는 묶음을 빨간색으로) (PR #388, Infra #126)¶

    • CmsIpBlockMgt 에 관찰 탭을 더했다(차단 목록 다음). 기간(일)과 IP 일부로 백엔드 로그(Log Analytics, 최근 30일)에서 같은 요청을 되풀이한 기록을 IP, 계정, 요청별로 묶어 본다 — 기준(IP + 계정 / IP 합산), 최대 횟수, 기준 넘음, 차단, 판정 창, 처음과 마지막 시각, UA. DB 에는 쌓지 않는다. 조회는 BE PR #334 의 /api/cms/log/cmsAzureLog/ipBlockObserve(ADMIN).
    • 최대 횟수가 지금 기준(서버가 쓰는 허용 횟수)을 넘는 IP + 계정 묶음은 빨간색(사용자 요청 — 지금 기준으로 얼마나 걸리는지 보려고). IP 합산 묶음은 차단 기준이 아니라 빨갛게 하지 않는다. 카드 안내에 "지금 기준으로 걸리는 것 N / IP + 계정 묶음 M".
      • IP 합산 묶음은 같은 요청이 기준 두 줄로 겹쳐 헷갈리므로 기본으로 숨기고, 조회 조건 "IP 합산 [보기]" 를 켤 때만 보인다(다시 조회하지 않고 거른다, 사용자 요청).
      • 빨간색은 행 스타일(getRowStyle)로만 준다. 요청 이름과 UA 는 요청하는 쪽이 정하는 값이라 HTML 렌더러를 쓰지 않는다(ag-grid 가 값을 이스케이프해 넣는다).
    • 상단 [저장] 은 관찰 탭에서도 꺼진다(저장할 것이 없다).
    • 수동 차단 확인창의 "BLOCK 으로 바꾸기 전까지는 막히지 않습니다" 경고를 OFF 일 때만 띄운다. LOG 에서도 수동 차단이 적용되게 바뀐 뒤(BE PR #331) 남아 있던 옛 문구다.

    IP 차단 — LOG 에서도 수동 차단이 적용된다는 안내, 차단 안내 창 문구, 관리 화면 저장 버튼 자리 (PR #387, Infra #126)¶

    • 백엔드 PR #331 로 LOG 모드에서도 수동 차단을 막게 되어(사용자 결정) 관리 화면 안내를 맞췄다.

    같은 요청을 되풀이한 IP 차단 — 관리 화면과 차단 안내 창 (PR #386, Infra #126)¶

    백엔드가 IP 마다 같은 요청을 세고, 동작이 BLOCK 이면 기준을 넘은 IP 를 막는다(백엔드 PR 에 판정과 차단이 있다). 설정, 차단 기록, 예외 IP 는 Oracle PKG_IP 에 있고 공통 프로시저 관문으로 다룬다. 프론트는 아래 둘이다.

    • 관리 화면 cms/setting/CmsIpBlockMgt(ADMIN 메뉴, 상단 버튼 초기화, 조회). 탭 셋이고 상단 조회는 보고 있는 탭만 조회한다.
      • 차단 목록: 기간(기본 7일 전~오늘), IP 일부, 상태(차단, 해제, 만료)로 조회한다. 풀리는 시각이 없으면 기간 없음, 남은 시간은 분으로 보인다. 왼쪽에서 IP 를 수동 차단(시간을 비우면 해제할 때까지)하고, 목록에서 상태가 차단인 행을 체크해 해제 사유와 함께 푼다. 해제는 그 IP 의 차단을 모두 풀어서 같은 IP 는 한 줄만 보낸다.
      • 예외 IP: 세지도 막지도 않는 IP. 행 추가, 삭제, 저장. IP 는 키라 새 행에서만 고친다.
      • 설정: 동작(OFF 끔, LOG 기록만, BLOCK 차단), 판정 창(초), 허용 횟수, 차단 시간(분), 해제 요청 메일 받는 주소. 운영에서 IP 판정이 nginx 로그와 맞는 것을 확인하기 전에는 BLOCK 으로 바꾸지 말라는 안내를 동작 옆에 두었고, BLOCK 으로 저장할 때 한 번 더 묻는다. 설정을 못 읽은 채로는 저장하지 않는다(빈 폼이 설정을 덮어쓰지 않게).
      • 저장(수동 차단, 해제, 예외 IP, 설정)이 끝나면 /api/ipBlock/reload 를 불러 모든 서버가 바로 다시 읽게 한다. 안 부르면 서버마다 최대 1분 뒤에 반영된다. 이 호출이 실패해도 저장은 끝난 것이라 경고만 한다.
      • dataset 의 PKG_IP 프로시저 6개는 빌드가 만드는 관문 허용 목록에 들어간다. 배포 뒤 MdmPackageMgt 의 [허용 목록 갱신] 을 누르지 않으면 이 화면은 다음 03:00 까지 막힌다.
    • 차단 안내 창(EIpBlockDialog, App.vue 최상단). 막힌 IP 의 요청은 백엔드가 429 + X-Ip-Blocked 헤더 + JSON 본문으로 끊는다. http 응답 인터셉터가 그 본문을 ipBlock 스토어에 넣고 창이 뜬다. 로그인 화면을 포함해 어느 경로에서든 창은 하나다.
      • 문구는 영어 고정이다(다국어, 메시지 코드 없음). IP, 차단 시각, 풀리는 시각(KST)을 보이고 닫기 버튼은 없다. [Request unblock] 은 /api/ipBlock/releaseRequest 로 관리자에게 해제를 요청하고, 보낸 뒤에는 보낸 시각을 보이며 꺼진다. [Refresh] 는 새로고침.
      • nginx 자체 속도 제한도 429 지만 헤더 없이 HTML 로 온다. 그건 창을 띄우지 않고 종전대로 처리한다.
      • quiet 요청은 reject, 화면 요청은 미결 Promise 다. 부팅의 $session 이 quiet 인데 미결로 두면 bootstrap().finally( app.mount ) 가 끝나지 않아 빈 화면이 된다. 로그인 화면은 ipBlocked 면 자기 오류 문구를 띄우지 않는다.

    FDS 오더 관리: 컨테이너 번호를 바꾸면 그 행의 TPSZ 만 조회한다 (PR #383, Infra #126)¶

    • FdsOrdMgt 컨테이너 그리드는 EQNO 칸 하나가 바뀔 때마다 모든 행의 TPSZ 를 다시 조회했다. 컨테이너 N 개를 붙여넣으면 조회가 N² 번 나가고(20개면 400번, 100개면 10,000번), 그 흐름 N 개가 동시에 돌았다.
    • 운영에서도 이 화면에서 IP 하나가 관문을 분당 수천 번 불렀고, nginx 초당 제한(429)과 504 가 났다. 최근 14일 상위 3개 IP 의 응답 중 약 44,000건이 같은 크기(196바이트)의 200 이었고, 따로 약 3,700건이 429 였다. nginx 로그에는 프로시저 이름이 없어 이 반복 조회로 보이는 것이고, 배포 뒤 이 화면의 분당 최대 요청 수가 떨어지는지로 확인한다.
    • 이제 바뀐 행만 조회한다. 붙여넣은 행은 줄을 세워 한 번에 4건까지만 보낸다(fnQueueTpsz). 응답이 끝내 안 와도($axios 는 알 수 없는 오류와 409 에 끝나지 않는 Promise 를 돌려준다) 30초 뒤 다음 조회에 자리를 내준다.
    • 조회를 기다리는 동안 번호를 다시 바꾸면 늦게 온 옛 번호의 응답은 버린다. 종전에는 그 응답이 새 번호의 TPSZ 를 덮어쓸 수 있었다.
    • fnGetTpsz 는 요청마다 dataset 을 새로 만든다. axios 요청 인터셉터가 비동기라, 동시에 보낼 때 공유 dataset 을 고쳐 쓰면 앞 요청이 뒤 번호를 싣고 나간다.
    • 달라진 것: 조회가 실패한 행은 종전에는 다른 행의 번호를 바꿀 때 덩달아 다시 조회됐다. 이제는 그 행의 번호를 다시 넣어야 다시 조회한다.
    • 그대로인 것: 번호를 지우면 TPSZ 도 지운다. SOC 오더(SOC=Y)는 조회하지 않고 TPSZ 를 손으로 넣는다. 조회 결과가 없으면 TPSZ 를 건드리지 않는다.
    • 실물 ag-grid 테스트(FdsOrdMgt/__tests__/tpszLookup.spec.ts)로 확인했다. 수정 전 코드에서는 20개 붙여넣기에 400번, 동시 20건이 나오고 옛 응답이 새 값을 덮는다.

      • 받은 뒤 선택을 푼다. 실패하면 선택을 남긴다. readonly 에서도 보이고, staging 에서는 뜨지 않는다. 파일이 없는 행은 뺀다.

    • fileDown 이 실패를 알린다: 서버 에러를 삼키지 않고 화면에 보일 문구로 reject 한다. 서버 JSON 의 message, 본문 없는 404 는 MSG000397, 그 밖에는 일반 실패 문구다. 전에는 404, 409 에도 화면에 아무 일이 없었다.
    • 잘린 zip 을 저장하지 않는다: application/zip 응답의 마지막 22바이트가 zip 끝 표지(50 4B 05 06)로 시작하지 않으면 실패로 본다. 서버가 중간에 실패해도 응답이 200 으로 올 수 있어서다(nginx 가 백엔드를 HTTP/1.0 으로 불러 끊김과 정상 종료를 구분하지 못한다).
    • 옛 시스템 첨부도 받는다: 그리드가 다운로드, PDF 뷰어, 선택 다운로드에 행의 COMP_CD 를 함께 보낸다. 서버가 그 값으로 선사별 옛 테이블(SKR_DOC_MST)을 찾는다. fileDown 은 FILE_SN 0 을 막지 않는다(옛 행의 첫 파일 번호). 전에는 옛 행이 다운로드도 PDF 뷰어도 404 였다.

    배포 뒤 기동 확인과 스모크 (PR #366, Infra #29)¶

    종전 게이트는 새 리비전의 provisioningState 가 Provisioned 인지까지만 봤다. 그건 "리비전이 만들어졌다" 는 뜻이라, nginx 가 떠서 실제로 새 번들을 내보내는지는 보지 않았다. 두 단계를 더 붙였다.

    기동 확인 — healthState 가 Healthy 가 될 때까지 기다린다. 레디니스 프로브(/healthz)를 통과했다는 뜻이다. 판정을 healthState 로 하는 이유는 정상일 때 runningState 가 Running 이 아니라 RunningAtMaxScale 로 나오기 때문이다. runningState 로 즉시 실패 판정은 하지 않는다 — Degraded 는 레플리카가 차례로 뜨는 롤아웃 중 잠깐 나올 수 있다.

    스모크 — 새 리비전 전용 FQDN 으로 세 가지를 본다. /healthz 가 200 인지, version.json 의 buildId 가 배포 전과 달라졌는지, / 가 200 인지. buildId 는 vite 가 빌드마다 새로 굽는 값이라 이게 바뀌었다는 것은 새 번들이 실제로 서비스된다는 뜻이다.

    앱 FQDN 이 아니라 리비전 전용 FQDN 을 치는 이유가 있다. 앱 FQDN 은 트래픽 전환 타이밍에 따라 옛 리비전이 받을 수 있어, 옛 번들을 보고 통과할 수 있다. 리비전 FQDN 은 외부에서 열린다.

    같은 커밋을 다시 돌리면 이미지 문자열이 같아 새 리비전이 생기지 않는다. 그 경우 옛 리비전을 보고 판정하게 되므로 게이트를 통째로 건너뛴다.

    백엔드 쪽 스모크는 백엔드 워크플로가 따로 한다. 여기서 /api 는 치지 않는다.

    자동 롤백은 넣지 않았다. 단일 리비전 모드와 레디니스 덕에 기동에 실패하면 옛 리비전이 그대로 서비스하고, 일시적 끊김으로 스모크가 한 번 실패했다고 멀쩡한 배포를 되돌리면 더 나쁘다. 게이트 실패는 잡 빨간불로 알리고 되돌리기는 사람이 한다.

    견적 승인 화면 그리드에서 돌 일 없는 편집 설정을 지웠다 (PR #361, Infra #98)¶

    Infra #98 4-3 에서 나온 정리다. CrsEstApproval 은 견적 작성 화면(CrsEstimate)의 그리드 정의를 복사해 만들어서, 보기 전용인데도 작성 화면의 편집 설정이 남아 있었다. 화면 동작은 바뀌지 않는다.

    왜 돌 일이 없나¶

    • 두 그리드(견적 목록, 견적 상세) 모두 defaultColDef.editable: false 이고, 열 단위로 editable 을 켜는 곳도, 실행 중에 켜는 곳(setColumnEditable(s))도 없다. 그래서 셀 편집기와 값 변환(valueParser)이 불릴 일이 없다.
    • 열의 값 변경 처리(onCellValueChanged, 안에서 setDataValue 로 상한을 넘는 값을 0 으로 되돌림)는 편집이나 setDataValue 로 값이 바뀔 때만 돈다. 이 화면은 그리드를 setItems(setRowData)로만 채우는데, 이 경로는 값 변경 이벤트를 내지 않는다.

    지운 것¶

    • 견적 목록: ESTIMATE_DATE, APP_DATE 의 날짜 편집기
    • 견적 상세
    • FM_UNIT, TO_UNIT: 숫자 편집기와 설정, 값 변환, 값 변경 처리
    • QTY: 텍스트 편집기와 설정, 값 변환, 값 변경 처리
    • HOURS, MCOST: 숫자 편집기
    • RESP: 선택 상자 편집기와 설정
    • 그래서 쓰지 않게 된 편집기 import 4개

    남긴 것¶

    • 표시용 설정(valueFormatter, 툴팁, 정렬)은 그대로다.
    • 상세 그리드 머리글의 필수 표시(AgEssentialHeader)는 화면에 보이는 것이라 이번에 건드리지 않았다.
    • 두 화면의 그리드 정의를 하나로 합치는 일은 하지 않는다. 겹치는 부분이 대부분 열 선언이고, 승인 화면의 회사, 통화, USD 합계, 100 USD 선택 규칙과 작성 화면의 편집 로직처럼 차이가 의도된 것이라 합치면 공통 정의가 오히려 복잡해진다.

    Infra #115. CrsEstApproval 의 조회를 SP_GET_EST → SP_GET_EST_NEW 로 바꾼다. 견적 조회 화면은 PR #350 에서 이미 넘어갔으므로, 이로써 SP_GET_EST 는 호출처가 없다.

    • 결과는 같다. .100 에서 선사 3개의 승인 조회를 전체 컬럼 양방향 MINUS 로 대조해 0행을 확인했다(SNKO/PUS12 14,726행, HALK/PUS01 11,184행, HSLI/INC07 1,795행).
    • 파라미터 이름과 순서가 SP_GET_EST 와 같다. 관문이 ALL_ARGUMENTS 를 이름으로 읽어 꽂으므로 화면에서 더 보낼 값은 없다.
    • 속도 이득은 거의 없다. 이 화면은 하루 1~3명이 쓰고 20초를 넘긴 호출이 0건이다. 받는 것은 file_yn 을 exists 로 바꾼 분 정도다.
    • 바꾸는 이유는 성능이 아니라 정리다. 지금은 같은 데이터를 보는 두 화면이 서로 다른 프로시저를 본다. 하나로 모으면 다음에 로직을 고칠 때 어느 쪽을 고쳐야 하는지 헷갈리지 않는다.
    • SP_GET_EST 는 DB 에 그대로 둔다. 되돌릴 일이 생기면 이 파일 한 줄로 돌아간다.

    DB 쪽 선행 조건은 없다. 운영에 지금 컴파일돼 있는 SP_GET_EST_NEW 도 APP_YN='Y' 가지를 그대로 갖고 있어 이 화면이 바로 탄다. 승인 전용 커서로 갈라진 새 본문을 컴파일하면 그때부터 그쪽을 탄다.

    허용 목록은 112 에서 111 로 줄어든다. 두 화면이 같은 이름을 쓰게 되기 때문이다. 이번에는 이름이 빠지기만 하므로 갱신 버튼을 당장 누르지 않아도 조회가 막히지 않는다. 백엔드가 들고 있는 옛 목록이 상위집합이라 그렇다. 다만 다음 기동이나 03:00 에 자동으로 맞춰지니, 정리 삼아 눌러 두면 깔끔하다.

    사용자 관리의 회사 코드 팝업은 자기 모듈 회사만 보인다 (PR #348)¶

    Infra #91 "#88 처리 뒤 남은 항목" 중 "회사 코드 선택 팝업이 모듈로 거르지 않는다".

    • CmsUserMgt 의 회사 코드 팝업 두 곳(조회 조건, 상세의 소속 회사)에 늘 USER_ID(로그인 사용자)를 넘긴다. 종전에는 조회 조건만, 그것도 수리장 관리자(CRS00)일 때만 넘겼다.
    • 팝업 쿼리(selectCorp)는 이 값으로 ADMIN 에게는 전부, 그 밖에는 SYSTEM_DIV 가 내 역할 앞 3자인 회사만 돌려준다. 서버 저장 판정(법인 범위)과 같은 규칙이다.
    • 자기 모듈은 사용자 소속 회사의 모듈이 아니라 역할로 정해진다. 예: CRS00 담당자는 소속이 SNKO(FDS)지만 CRS 회사를 다룬다.
    • 종전에는 모듈 관리자가 범위 밖 회사를 고를 수 있었고, 저장 때 서버의 법인 범위 판정(백엔드 PR #223)이 거절했다. ADMIN 화면은 바뀌지 않는다.
    • 포트 그리드의 회사 칸은 서버 판정 대상이 아니라 그대로 둔다.

    비밀번호 초기화 화면에서 하는 일 없던 사전 확인 호출을 뺀다 (PR #346)¶

    Infra #91 판단 항목 "비밀번호 찾기". 백엔드 PR #292 와 짝이다.

    • src/pages/login/pw-init/index.vue: "Reset the Password" 가 /api/auth/find/password/user 를 먼저 부르고 나서 /api/auth/find/password 를 불렀다. 앞의 호출은 메일 발송이 주석 처리돼 하는 일이 없었고, 응답의 인증번호도 쓰지 않았다. 이제 /api/auth/find/password 만 부른다.
    • 백엔드는 그 API 를 지운다. 이 PR 이 먼저 배포돼야 한다.
    • 발송에 성공하면 같은 화면에서 다시 누를 수 없게 막는 동작은 그대로다. 종전과 달리 발송이 실패하면 다시 시도할 수 있다.

    메일 팝업의 From 칸을 숨긴다 (PR #347)¶

    Infra #91 판단 항목 "메일 발신자".

    • CmsEmailPopup(TES 4개 화면, FDS Invoice 에서 여는 메일 팝업)의 From 칸을 숨긴다(v-show="false", 템플릿에는 남겨 둔다). 값은 메일 양식 프로시저가 선사 공용 발신함(sendonly@…)으로 채우고, 보낼 때 그대로 넘긴다.
    • From 이 비었을 때 로그인 사용자 메일로 채우던 보정은 없앴다. 백엔드 PR #295 가 공용 발신함 말고는 거절하므로, 채워 봐야 서버에서 실패한다. 비어 있으면 From 필수 검사가 안내한다.
    • 서버 검사(백엔드 PR #295)가 실제 차단이고, 이 PR 은 화면을 그에 맞춘다. 배포 순서는 상관없다.

    문서: 비밀번호 찾기 안내와 "No endpoint" 응답 코드를 맞춘다 (PR #349)¶

    견적 조회가 개선본 프로시저를 쓴다 (PR #350)¶

    Infra #115. CrsEstimate 의 조회를 SP_GET_EST → SP_GET_EST_NEW 로 바꾼다.

    • 프로시저는 운영에 이미 컴파일돼 있다. 결과는 같다 — .100 에서 선사 3개(SNKO/HALK/HSLI) 체크섬을 원본과 대조했다.
    • 파라미터 이름과 순서가 SP_GET_EST 와 같다. 관문이 ALL_ARGUMENTS 를 이름으로 읽어 꽂으므로 화면에서 값을 더 보낼 것은 없다.
    • 개선분은 file_yn 을 count(UNION ALL) 에서 exists or exists 로 바꾼 것이다. 약 -12%. 평소 2.1초가 1.9초쯤 된다.
    • 승인 화면(CrsEstApproval)은 SP_GET_EST 를 그대로 쓴다. 한쪽만 바꿔 운영에서 비교하려는 것이고, 하루 1~3명이 쓰는 저빈도 화면이라 급하지 않다.

    배포 뒤 관리자 화면에서 허용 목록 갱신 버튼을 눌러야 한다(Infra #92). 목록은 빌드가 자동으로 만들지만 백엔드는 기동, 매일 03:00, 갱신 버튼 때만 다시 읽는다. 누르지 않으면 다음 03:00 까지 견적 조회가 거절된다.

    CI 의 Trivy 를 GitHub 릴리스에서 직접 받고, 실패해도 PR 을 막지 않게 한다 (PR #345)¶

    2026-11-03 밤부터 PR 의 CI(ci.yml) Trivy 단계가 설치에서 실패하게 됐다. 백엔드 PR 에서 먼저 드러났다(백엔드 #289).

    • trivy-action@v0.36.0 이 부르는 설치 단계(setup-trivy)는 Trivy 본체를 get.trivy.dev 에서 받는다. trivy.dev 도메인이 2026-11-03 21:34 UTC 에 등록업체 주차 페이지로 바뀌면서 이 주소가 DNS 에서 사라져 curl 이 exit 6 으로 죽는다(상류 이슈 aquasecurity/setup-trivy #42).
    • 캐시는 PR 마다 따로 저장돼 다른 PR 이 재사용하지 못한다. 그래서 새 PR 은 매번 본체를 새로 받는다.

    바꾼 것¶

    • Install Trivy 단계를 새로 넣었다. GitHub 릴리스에서 trivy_0.70.0_Linux-64bit.tar.gz 를 받아, 워크플로에 고정한 sha256 과 대조한 뒤 PATH 에 올린다. 버전은 trivy-action@v0.36.0 의 기본값과 같다. 다른 Trivy 단계처럼 빌드 성패와 무관하게 돈다(if: always()).
    • 취약점 스캔과 SBOM 단계에 skip-setup-trivy: 'true' 를 줘 위에서 설치한 본체를 쓴다.
    • Trivy 단계(설치, 스캔, SBOM)에 continue-on-error: true 를 붙였다. 원래 보고만 하는 단계라, 외부 장애로 스캔을 못 해도 PR 을 빨간불로 만들지 않는다. 실패는 그 단계 로그에 남고, 실행 요약에는 "결과 파일 없음" 이 나온다.
    • 문서: 빌드와 배포의 CI 절.

    • docs-dev/auth.md: SSO 유입 절을 폐쇄 기록으로 바꿨다.

    수리장 관리자 CRS00 — 사용자 관리에서 소속 회사 REPAIR 고정 (PR #343)¶

    수리장 관리자 역할 CRS00 이 사용자 관리(CmsUserMgt)만 쓰도록 화면을 맞췄다. 판정은 세션 역할에 CRS00 이 있고 ADMIN 이 아닐 때다(isRepairAdmin).

    • NEW 를 누르면 상세의 CORP 가 REPAIR 로 채워진다. 관리자가 팝업에서 REPAIR 를 고른 것과 같게 이름과 관계 회사 행(selectCorpRel)도 불러온다.
    • 상세 CORP 칸은 읽기 전용이다. 기존 사용자를 열었을 때도 바꿀 수 없다(돋보기 버튼도 함께 꺼진다).
    • 조회 조건 CORP 팝업은 SYSTEM_DIV 가 CRS 인 회사만 보인다. 기존 selectCorp 의 USER_ID 조건(세션 사용자 역할의 앞 3자)을 쓴다. 칸에 코드를 직접 입력해도 같은 범위에서만 찾는다.

    API 허용 역할과 회사 관리 차단은 백엔드 PR #284, 역할 행 등록은 사용자가 DB 에 했다. 역할이 없는 계정에는 아무 변화가 없다.
