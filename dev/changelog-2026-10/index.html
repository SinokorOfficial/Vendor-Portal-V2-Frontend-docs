    FdsOrdMgt 시간 입력 에러와 검증 버그 수정 (PR #255, Infra #82)¶

    73 분해 중 발견해 그대로 옮겨 두었던 fds/FdsOrdMgt 의 기존 버그를 고쳤다.¶

    • 시간 오입력 시 스크립트 에러: 시간(오더 FD_ETA_TM/FD_ETD_TM, 컨테이너 OFD_TM/IED_TM)이나 Feeder Movement 미입력 상태의 OFD/IED 를 잘못 넣으면 경고와 칸 비우기 뒤에 node.setFocusedCellByRowIndex 에서 TypeError 가 났다. getSelectedNode() 의 RowNode 에는 이 메서드가 없다(어댑터 메서드). 해당 그리드 어댑터로 부르게 바꿔 이제 그 칸으로 포커스가 돌아간다(컨테이너 그리드는 편집까지 시작).
    • fnTimeValidation: 숫자 4자리(HHMM)가 아니면 false. 전에는 '12', 'abcd' 가 parseInt NaN 비교로 통과했다. 빈 값은 전처럼 통과.
    • fnSearchValidation: From > To 메시지를 만들기만 하고 띄우지 않던 것을 경고 후 조회를 막도록 고쳤다.
    • 정리(동작 동일): fnSave 의 fnSearchCntr('') 를 { value: '' } 로 명시, 호출처 0 인 fnTimeFormatValidation 삭제, fnSetVsl 의 n² 중복 루프를 한 번으로.
    • expandCntrRows(EQNO 있는 행과 빈 행이 섞이면 빈 행 자리에 첫 행 복사본)는 프로시저가 섞인 행을 돌려주는지 확인이 필요해 보류.
    • 테스트: __tests__/gridOptions.spec.ts 5건 추가(목 어댑터로 세 지점 검증), dataUtil.spec.ts 의 시간 검증 기대값을 고친 동작으로 바꾸고 경계 케이스 추가.
    • 컨테이너 그리드 OEV_TM/IFE_TM 시간 검사가 실행되지 않던 것: 시간 검사 코드가 OFD/IED 분기 안에 있어, 조건에 적혀 있던 OEV_TM/IFE_TM 은 그 분기에 들어오지 못했다. 시간 검사를 분기 밖으로 빼 네 컬럼 모두에 건다(OFD_TM/IED_TM 의 순서와 동작은 그대로).

    변경 이력을 PR 마다 파일 하나로 (PR #254, BE #208)¶

    PR 여러 개가 changelog.md 의 같은 자리(그 달 섹션 맨 위)에 항목을 끼워 넣어, 하나를 머지하면 나머지가 매번 충돌했다. 파일도 900줄 가까이 길어졌다.

    • 항목은 docs-dev/changelog/YYYY-MM/YYYYMMDD-<브랜치슬러그>.md 에 파일 하나로 추가한다. 새 파일만 생기니 PR 끼리 충돌하지 않는다. 작성 규칙은 같은 폴더 README.md.
    • 빌드 때 MkDocs 훅(docs-tools/changelog_hook.py)이 조각을 모아 changelog.md(월 목록)와 월별 페이지(changelog-YYYY-MM.md)를 만든다. 추가 패키지는 없다. 기존 changelog.md 링크는 그대로 동작한다.
    • 기존 106개 항목은 내용을 바꾸지 않고 옮겼다(YYYYMM00-NN-…, 원래 순서 보존). 제목 단계만 ### → ##.
    • 백엔드 레포도 같은 훅, 같은 형식으로 바꿨다.

    셀 편집 변경 감지: 0 과 빈 값 구분 (사용자 결정 2026-10-08)¶

    이 항목은 화면 동작이 바뀐다. 셀 편집 비교가 newValue || '' 와 oldValue || '' 를 비교해 0 → '', '' → 0, 0 → null, null → 0 이 U 로 잡히지 않았다. 그 행에 다른 변경이 없으면 저장 대상(getItems())에서 빠져, 수량이나 금액을 0 으로 바꾸거나 0 을 지운 수정이 저장된 것처럼 보이고 실제로는 저장되지 않았다.

    • 새 규칙: null, undefined, '' 는 같은 빈 값, 숫자 0 은 따로 구분. 0 이 아닌 값은 종전과 같다(엄격 비교라 0 과 '0' 은 다름, false, NaN 은 빈 값)
    • 이제 잡힘: 0 → '', '' → 0, 0 → null, null → 0, 5 → 0, 0 → 5
    • 계속 안 잡힘: '' → null, null → undefined, undefined → ''(텍스트 편집기가 null 셀을 열었다 닫는 소음, Delete 키로 빈 칸을 지우는 경우)
    • 숫자 편집기 AgNumberBoxEditor: 값이 없는(undefined) 칸을 열었다 그냥 닫기만 해도 0 을 커밋해, 위 규칙에서는 손대지 않은 행이 U 가 됐다. 사용자가 실제로 입력했는지(input 이벤트, 숫자 키로 편집 시작)를 보고, 입력이 없으면 원래 값을 돌려주게 고쳤다(사용자 결정 2026-10-08). 값이 있던 칸을 지우면 0 이 되는 동작은 그대로다.
    • 테스트: components/manual/ag-grid/vue/__tests__/AgNumberBoxEditor.spec.ts(jsdom 에 실물 dx-number-box, 6건). 이를 위해 vitest.config.ts 에 @vitejs/plugin-vue 를 넣어 .vue 를 읽게 했다.

    CRS 견적 리포트 — 금액·합계 소수 둘째 자리¶

    • 견적 목록(PRINT): 금액 칸(OWN~VIP, TOTAL)과 GRAND TOTAL 을 천단위 콤마 + 소수 둘째 자리로(fmtInt → fmtAmt). 레거시 서식 {0:#,#} 이 정수로 반올림해 센트가 사라졌다. 0 은 종전처럼 빈 칸, 건수는 정수 그대로.
    • 견적서 상세(PRINT): 하단 합계표의 Hours 열을 소수 둘째 자리로(다른 열은 이미 둘째 자리). Grand Total Hours 는 화면에서 상세행을 더한 값이라 원값 그대로면 2.3000000000000003 같은 부동소수 찌꺼기가 보일 수 있었다. 상세행 Hours 와 상단 Labor Cost 는 현행 유지(사용자 결정).

    CrsEstimate — 저장 전 견적을 삭제하면 '권한 없음'이 뜨던 문제 (PR #248)¶

    • 증상: 2026-10-07 PUS14 가 견적 삭제 시 You do not have permission.(409, 에러로그 기록). 그런데 나중에 fn_can_access_est('PUS14','HALK','PUS142610000022') 는 Y 였다.
    • 원인: NEW 를 누르면 저장 전인데도 SP_GET_NEW_EST 가 다음 견적번호를 미리 받아 화면에 채운다. 그 상태에서 DELETE(또는 상세 0행으로 저장 → fnDelete)를 누르면 DB 에 없는 번호로 SP_DEL_EST 가 불리고, 소유 게이트 fn_can_access_est 는 견적이 없으면 N 이라 권한 거절로 나갔다. 이후 같은 번호로 저장돼 지금은 Y.
    • 수정: SP_DEL_EST 가 게이트 앞에서 견적 존재부터 보고, 없으면 RESULT='X' + 안내 문구를 돌려준다(DB, .3 반영 완료). 화면은 X 면 서버 삭제 없이 화면만 비우고 그 문구를 알린다.
      • 화면의 serverChk 는 컨테이너 번호를 입력할 때도 false 가 돼 "저장된 견적인가" 판단에 쓸 수 없어서, 판정은 서버에 맡겼다.
      • DB 반영 전에는 종전과 같다(X 가 안 오므로 영향 없음).

    비밀번호 정책 — 내 정보 저장 전 검사 + 메시지 코드화 (Infra #77)¶

    업로드 화면 7종 — 저장 전 형식·바이트 검사 (공용 ValidateUtil 4종) (PR #238)¶

    • 계기: LCH24(태국 람차방) 견적 엑셀 저장이 ORA-06502 로 실패했다. 1행 EQ_NO 맨 앞에 태국 성조 부호 U+0E49(태국어 자판에서 h 키)가 붙어 있었다. 화면 검사는 .length !== 11 이었는데 .length 는 UTF-16 단위라 이 문자를 1자로 세어 11자리로 통과했다. DB 는 AL32UTF8 에서 3바이트라 13바이트 → VARCHAR2(11 BYTE) 초과. 저장 프로시저가 IN 커서를 임시 테이블 %rowtype 으로 fetch 하므로 칸 하나만 넘쳐도 묶음 전체가 실패한다(같이 보낸 정상 행까지 미저장).
    • 공용 함수(util/premitive/ValidateUtil.ts) — 넷 다 true/false 를 돌려준다. true 면 입력값을 그대로 쓰고 false 면 호출부가 안내한다(여러 행을 모아 창 하나로 보여 주는 화면이 있어 함수 안에서 메시지를 띄우지 않는다).
      • isAlnum(value, length?, mode = 'exact', allow = '') — A-Z a-z 0-9(+allow 문자)만. 빈 값(공백뿐 포함)은 false. 'exact'(기본) 정확히 그 자릿수, 'max' 1 ~ 그 자릿수. ASCII 만 허용하니 글자 수 = 바이트 수라 DB VARCHAR2(n BYTE) 한도와 그대로 맞는다.
      • isDateFormat(value, 8 | 12) — 8 은 yyyymmdd, 12 는 yyyymmddhh24mi. 실제 있는 날짜·시각인지 본다(20260231, 2400, 1260 차단).

      • (DB, .3 반영 완료) PKG_FDS.sp_get_errcheck 의 미등록 피더 선박 검사가 x.emp_no = p_user_id 였는데 sp_set_eqmv_new 는 사용자를 emp_nm 에 넣어 검사가 한 번도 걸리지 않았다 → x.emp_nm 으로 정정. ⚠️ 이제 tb_fds_fdvsl(use_yn='Y')에 없는 피더 선박은 저장이 거절된다(.100 2025년 이후 주문 18,726건 중 201건, 약 1.1%가 미등록 선박 — HUI, XF6, HB28 등).
    • 검증: ValidateUtil.spec.ts 8종 추가(실사례 문자열, 빈 값, 자릿수 부족/초과, 'max', 허용문자와 문자 클래스 이스케이프, 바이트, 윤년, 24시/60분) — 전체 103/103 통과. 화면마다 검증 코드를 원본에서 잘라 실행한 하네스로 실사례 차단과 정상 경계값 통과를 확인했다(TesTugExpn 은 .100 TB_TES_TUG 2,454행 전부 통과). vue-tsc --noEmit exit 0, ESLint 0.

    에러 로그 — 다른 행을 고르면 메시지를 맨 위부터 (핫픽스)¶

    • CmsErrorLogList 의 ERR_MSG 텍스트 영역이 내용이 바뀌어도 스크롤 위치를 유지해, 긴 메시지를 내려 본 뒤 다른 행을 고르면 새 메시지의 중간이 보였다.
    • 행 선택(onRowSelected) 때 $nextTick 뒤 내부 textarea.dx-texteditor-input 의 scrollTop 을 0 으로 되돌린다(fnScrollErrMsgTop).

    CrsEstUploadExl — 옛 저장 프로시저로 되돌리던 스위치 제거 (PR #236, BE #186, Infra #49)¶

    • USE_NEW_SP_FOR_ALL/NEW_SP_TEST_USERS 스위치와 옛 데이터셋(dataset.SAVE → SP_SET_EST4EXL)을 지웠다. 저장은 항상 SP_SET_EST4EXL_NEW 다.
    • 근거: 2026-09-17 전체 적용 후 2주간 운영 무사고(데드락 0, HSLI 정상, order_no 가드 정상 — Infra #49 2~4번 종결). 옛 경로 호출은 09-20 이후 0건이다. 옛 경로는 대량 저장이 240초 벽에 걸리는 구조라 되돌려도 해결이 안 된다.
    • 이 스위치가 전역 쿼리 타임아웃을 막고 있었다(옛 경로는 246초까지 걸려, 그보다 짧은 타임아웃을 걸면 스위치를 못 쓴다). 같은 날 BE 에 150초 타임아웃을 넣었다.
    • 원본 프로시저는 DB 에 그대로 있다. 다시 써야 하면 이 커밋을 되돌리면 된다(단 그때는 BE 타임아웃 150초에 걸린다).

    선사 전환 시 봉투(COMP_CD)가 화면과 어긋나던 경로 둘 차단¶

    • 증상: 협력사 계정이 자기 HALK 견적을 삭제하려는데 You do not have permission. 요청을 보니 ESTIMATE_NO 는 HALK 것인데 COMP_CD 는 SNKO 였다. 서버 소유검증은 정상 동작한 것이고, 프론트가 봉투를 틀리게 실어 보낸 것이다.
    • 원인 1 — 캐시된 탭: TabWorkspace 가 <keep-alive> 로 여러 화면을 동시에 캐시하는데, 선사 전환(EContentLayout.changeCompany)은 그때 보이던 화면 하나만 fnReset 한다. 다른 탭은 옛 선사 데이터를 그대로 들고 있다가, 거기서 삭제하면 봉투만 새 선사가 된다.
    • 원인 2 — 화면 간 인자전달: sendPageArgs 로 열린 화면은 EContentLayout 의 mounted 가 기본 선사(MAIN_YN='Y')로 스냅하는데, 받은 데이터는 송신 화면 선사 것이다(CrsEstUploadExl → CrsEstimate).
    • 조치
      • ui 스토어에 applyCompany(compCd) 신설 — activeCompany/activeCustCd/activeLocCd 를 한 묶음으로 교체. companyList 조회가 EContentLayout 안에만 있던 것을 끌어올렸다.
      • EContentLayout: changeCompany 를 applyCompany(봉투·스타일만) + 리셋으로 분리하고 onActivated 에서 그 화면이 보던 선사로 봉투를 되돌린다. ★onActivated 에서 fnReset 은 부르지 않는다 — 복원된 그리드를 지우면 의미가 없다. 선택을 기억하도록 changeCompany 가 codeMapSel 을 갱신한다(종전엔 created 에서 한 번만 세팅돼 되돌릴 값이 없었다).
      • sendPageArgs → receiveArgsMeta({ COMP_CD }), mixins/page.deliverPageArgs 가 onReceiveArgs 직전에 봉투를 송신 선사로 맞춘다. $nextTick 안에서 적용해 모든 activated 훅 이후가 되도록 했다.
    • ★레거시도 같은 결함이었다 — UContentLayout.changeCompany 가 V2 와 동일 코드($parent?.fnReset() + 전역 commit)다. V2 회귀가 아니라 이관된 결함이다.
    • 하지 않은 것: 선사 전환 시 모든 탭 리셋 / 탭 전부 닫기 / 그리드 행에서 COMP_CD 꺼내기. 앞의 둘은 사용자 작업이 날아가고, 셋째는 다른 선사 컨텍스트에서의 조작을 허용하는 셈이다.
    • 상세: 상태관리 — 선사 전환은 applyCompany 로

    견적 업로드 — 클리닝 삭제 컬럼(DEL4CLEANING) 노출 보류 (핫픽스)¶

    • CrsEstUploadExl 의 onModelUpdated 가 ISCLEANING === 'Y' 행이 있으면 DEL4CLEANING 컬럼을 보이게 하던 로직을 주석 처리했다. 해당 기능이 아직 오픈 전이라 운영 화면에 노출되면 안 된다(2026-10-02).
