    const remaining = new Map()
resultList.forEach( file => remaining.set( file.ESTIMATE_NO, ( remaining.get( file.ESTIMATE_NO ) ?? 0 ) + 1 ) )
// 워커 안, 성공·실패를 가리지 않고 감소시킨 뒤
if ( left === 0 && uploaded.some( done => done.ESTIMATE_NO === file.ESTIMATE_NO ) ) {
    await this.fnSaveFile4Portal( { ESTIMATE_NO: file.ESTIMATE_NO } )
}

    ⚠️실패분도 감소시켜야 한다. 빼먹으면 한 장이라도 실패한 견적은 0 에 닿지 못해 영영 미러되지 않는다. 견적이 다르면 mngt_no 가 달라 DELETE/INSERT 가 겹치지 않으므로 동시에 돌아도 안전하다.

    2. 업로드 중 탭 닫기 경고¶

    먼저 '창을 닫는다'가 팝업이 아니라 브라우저 탭임을 확인했다. 팝업(다이얼로그)을 닫아도 업로드와 미러는 끝까지 돈다 — Vue 컴포넌트를 unmount 해도 진행 중인 async 는 멈추지 않고, http 에 AbortController 가 없어 요청도 취소되지 않는다.

    흐름을 끊는 것은 탭 닫기·새로고침·브라우저 종료 뿐이라, 업로드가 도는 동안만 beforeunload 를 건다.

    ⚠️경고 문구는 지정할 수 없다. 2016년 이후 모든 브라우저가 returnValue 를 무시하고 자체 문구만 보여준다 — 그래서 MSG 코드를 새로 쓰지 않았다.

    파일 다운로드 뒤 blob URL 해제 (PR #310, Infra #95)¶

    첨부, 템플릿 같은 파일 다운로드($axios.fileDown, $axios.fileOriginDown)는 받은 내용을 blob URL 로 만들어 앵커로 내려받는다. 다 쓴 URL 을 해제하는 revokeObjectURL 에 URL 이 아니라 앵커 요소를 넘기고 있어서 해제가 한 번도 되지 않았다. 그래서 내려받을 때마다 파일 크기만큼 탭 메모리에 남았고, 탭을 닫거나 새로 고칠 때까지 풀리지 않았다.

    • util/http/index.ts 의 processFileDown 이 만든 URL 문자열을 해제한다.
    • click() 직후 바로 해제하면 브라우저가 다운로드를 시작하기 전에 URL 이 사라질 수 있다(Firefox 등). 같은 파일의 PDF 뷰어(pdfViewer)처럼 10초 뒤에 해제한다.
    • 앵커는 문서에 붙이지 않고 만들어 바로 누르므로 뗄 것이 없다.
    • 사용자에게 보이는 변화는 없다. 내려받는 파일과 파일명은 그대로다.

    테스트 1건을 더했다(전체 200 → 201). 다운로드 응답을 흉내 내고 가짜 타이머로 해제 시점을 본다. 고치기 전에는 click() 직후 앵커 요소로 해제를 불러 실패하고, 고친 뒤에는 10초 뒤 만든 URL 문자열로 한 번 해제한다.

    지금 터지는 버그는 아니다¶

    이 화면은 e-attach-file-grid 에 multi-select 를 넘기지 않아 그리드가 단일선택이다 (AgGridAdapter 기본값 rowSelection: 'single', 체크박스 컬럼 없음). 그래서 컴포넌트의

    items.filter( … ).forEach( item => this.$emit( 'deleted', item ) )

    는 늘 1건만 올리고, fnDelFile4Portal 도 삭제 1회당 1번만 불린다. 업로드 쪽 uploaded 는 파일당이 아니라 요청당 1회라 fnSaveFile4Portal 도 마찬가지다.

    왜 그래도 고치나¶

    그 전제가 깨지는 순간 — 이 화면에 multi-select 를 다는 순간 — 종전 코드는 조용히 틀린다. dataset.DEL_FILE4PORTAL[0].PARAM 을 덮어쓰면 N 개 요청이 같은 객체를 참조하는데, axios 는 본문 직렬화를 프로미스 체인 뒤로 미루므로 그때는 루프가 이미 끝나 PARAM 에 마지막 파일명만 남는다.

    의도   DELETE a.jpg / DELETE b.jpg / DELETE c.jpg
실제   DELETE c.jpg / DELETE c.jpg / DELETE c.jpg

    앞엣것들은 포탈 미러(skr_doc_mst)에 남고, 남은 미러는 폴백이 파일을 되살려 뷰어 550 을 만든다.

    전제가 없는 호출부는 실재한다. CrsFileUploadPopup 은 호출부가 forEach 로 루프를 돌아 처음부터 N>1 이었고, 같은 패턴을 FE #279 에서 걷어냈다. 같은 모양이 여기 한 군데 더 남아 있어 전제가 깨지기 전에 미리 치운다.

    단, FE #279 에서 관측된 장애는 FTP 동시 전송 버스트였고(30초에 81건, 한 장이 16.6초에 사망), 공유 param 은 그 루프를 고치다 코드를 읽고 함께 잡은 것이다 — 그 경로로 실제 잘못 반영된 견적이 있었는지는 확인하지 않았다.

    어떻게 찾았나¶

    FE #279 뒤 SP_SET_FILE4PORTAL 호출량이 줄 줄 알았는데 그대로였다(일 1,400여 건 유지). 호출처를 프로시저 이름으로 다시 훑어 CrsEstimate 를 찾았다. 처음에 .upload() 기준으로만 훑어 놓쳤던 곳이다 — 이 화면은 업로드가 아니라 삭제 경로로 프로시저에 닿는다.

    탭을 옮겼다 돌아오면 스크롤 위치 복원 (PR #298, Infra #84)¶

    레거시에 있던 기능이 이관 때 빠졌던 것을 되살렸다. 긴 그리드를 내려 보다가 다른 탭에 다녀오면 본문과 그리드가 맨 위로 돌아가 있었다.

    원인¶

    • TabWorkspace 의 <keep-alive> 는 탭을 옮길 때 화면 DOM 을 문서에서 떼어 냈다가 다시 붙인다. 이때 브라우저가 화면 안의 스크롤 위치를 전부 0 으로 버린다.
      • 실측(Chromium, Vue 3 keep-alive, ag-grid 25.3): 본문 1200, 그리드 12500(500행째)까지 내린 뒤 다녀오면 0 과 0(0~7행)
    • 레거시는 scroll mixin 의 beforeRouteEnter/beforeRouteLeave 가드로 위치를 저장하고 되돌렸다. 이관 때 코드는 옮겼지만 vue-router 4 는 mixin 의 라우트 가드를 부르지 않아 V2 에서는 한 번도 돌지 않았다.

    조치¶

    • 새 scrollRestore mixin 을 pageMixin 에 넣었다. 화면 루트에 capture 단계 scroll 리스너를 하나 달아 스크롤할 때마다 요소별 위치를 기록하고, activated 에서 되돌린다.
      • deactivated 에서 저장하지 않는 이유: Vue 는 DOM 을 떼어 낸 뒤에 deactivated 를 부르므로 그때 읽으면 이미 0 이다(실측).
      • 떼어 낸 상태에서 난 scroll 은 기록하지 않고, 화면에서 사라진 요소는 되돌리지 않고 기록에서 뺀다.
      • 실측에서 본문과 그리드 모두 정확히 돌아왔고, 그리드도 500~507행을 다시 그렸다.
    • 대상은 pageMixin 을 쓰는 화면이다. 우클릭 Refresh 와 탭을 닫았다 다시 연 화면은 새로 마운트되므로 맨 위에서 시작한다(종전과 같다).

    지운 것¶

    • 돌지 않던 옛 scroll mixin
    • ui 스토어의 scrollMap, saveScrollMap, deleteScrollMap 과 그 테스트 1건

    ③ 행 추가가 앞서 지운 행의 삭제 기록을 지웠다 (1-9 ②)¶

    행 추가가 선택 행 아래에 사본을 끼우려고 clear() 후 setItems(getRows) 로 다시 깔았다. setItems 는 변경분 캐시를 비우므로 "삭제 → 행 추가 → 저장" 이면 삭제(D)가 저장에 안 갔다. 저장이 getRows()(그리드 행)와 getItems()(캐시)를 합쳐 보내는데, 지운 행은 캐시에만 있기 때문이다.

    어댑터에 이미 있는 insertItem(item, index)(applyTransaction({ add, addIndex }))로 같은 자리에 끼운다. 캐시를 건드리지 않아 D 기록과 다른 행의 수정 기록이 남는다.

    • 끼우는 위치는 종전과 같다(addIndex 와 종전 splice 둘 다 모델 순서 기준).
    • 새 행의 BATCH_FLAG 는 insertItem 이 I 로 단다. 저장 때 4화면 모두 D 가 아닌 행을 U 로 바꿔 보내므로 서버에 가는 값은 같다.
    • 덕분에 "행 추가 → 그 행 삭제" 는 이제 아무것도 보내지 않는다. 종전에는 서버에 없는 행의 D 를 보냈다.
    • setItems 가 하던 선택 해제는 deselectAll() 로 유지한다. 안 하면 원본 행이 선택된 채로 남아, 이어서 누른 삭제가 원본과 새 행을 함께 지운다.

    • 떼기: onDeactivated, onUnmounted

    • 이미 활성인 탭 안에 늦게 마운트된 레이아웃은 첫 activated 를 받지 못한다. Home 관리자 대시보드가 비동기로 띄우는 MdmNotice 가 그렇다

    컨테이너 무브 업로드 — 다시 저장하면 입력한 행이 사라지던 문제 (PR #285, Infra #87)¶

    • 검증 경고를 보고 그 행을 고친 뒤 다시 저장(고친 행까지 사라졌다)
    • 프로시저가 거절한 뒤 다시 저장

    원인¶

    저장 버튼이 빈 행을 걸러낸 뒤 검증하기 전에 setItems(mvData) 로 그리드를 다시 깔았다.

    • setItems 는 변경분 캐시(getItems())를 비운다.
    • 화면을 열 때 깔리는 빈 행 300개와 엑셀 업로드 행은 addItem 으로 들어와 BATCH_FLAG='I' 를 단다.
    • 캐시(CacheState.update)는 I 행을 고쳐도 다시 넣지 않는다. 추가할 때 이미 캐시에 있다고 보기 때문이다.

    조치 (fnSave, fnSaveValidation)¶

    • 그리드를 다시 깔지 않고 빈 새 행(I)만 지운다(removeItems). I 행은 지우면 캐시에서도 빠지고, 입력한 행은 캐시에 그대로 남는다.
    • 검증은 저장할 행만 본다. 다시 깔지 않으면 조회해 온 행 중 고치지 않은 행도 그리드에 남는데, 옛 데이터가 지금 형식 검사에 걸려 손대지 않은 행 때문에 저장이 막히면 안 되기 때문이다.
    • 저장할 행이 없으면 MSG000391(변경된 내용이 없습니다)로 멈춘다. 종전에는 빈 저장이 "저장되었습니다" 로 끝나고 그리드가 비었다.

    • 조회 후 일부만 고쳐 저장할 때 나머지 조회 행이 화면에서 사라지지 않는다.
    • 삭제한 행이 저장 직전에 그리드에 다시 나타나지 않는다.

    저장 성공 뒤에는 프로시저 결과 행으로 그리드를 다시 까는데, 이 행에는 BATCH_FLAG 가 없어 고치면 U 로 잡힌다(같은 함정 없음).

    견적 엑셀 업로드 저장 시 TOTAL COST 빈 값 ORA-01400 (PR #278)¶

    CrsEstUploadExl 에서 저장을 누르면 아래 에러가 났다.

    어디서 NULL 이 들어갔나¶

    두 경로가 있었고 한 곳에서 둘 다 막힌다.

    경로 흐름
    그리드 ADD 로 만든 행 estGridAddRow 의 newItem 에 TOT_COST_ORG 키 자체가 없다 → undefined
    엑셀의 공백만 든 셀 fnExcelValidaion 은 ' ' 를 값 있음으로 보고 통과시키고, 그 다음 줄의 .trim() 이 '' 로 만든다 → Oracle 에서 빈 문자열 = NULL

    엑셀의 완전 빈 셀은 종전처럼 fnExcelValidaion 이 행째 버린다. 바뀌지 않았다.

    ★컬럼 DEFAULT 0 은 이 경우를 못 막는다¶

    TMP_CRS_EST4EXL.TOT_COST_ORG 는 NOT NULL DEFAULT 0 이지만, DEFAULT 는 INSERT 문에서 그 컬럼을 아예 생략했을 때만 적용된다. 프로시저가 NULL 을 명시적으로 넘기면 DEFAULT 가 걸리지 않고 그대로 ORA-01400 이다. 그래서 보내는 쪽에서 채운다.

    검토했으나 고치지 않은 것¶

    fnExcelValidaion 이 QTY·TOT_COST_ORG 를 ObjectUtil.isEmpty(data.QTY) 로 검사한다. ObjectUtil.isEmpty 는 숫자를 받으면 Object.keys(n).length === 0 이라 항상 true 를 돌려주므로, 값이 숫자라면 멀쩡한 행이 말없이 버려질 자리로 보였다.

    실제로는 그런 일이 없다. 엑셀 파서가 모든 셀을 문자열로 돌려주기 때문이다.

    // VmsExcelFacade.java:84 — DataFormatter.formatCellValue() 의 반환형은 String
data.put(headerName, cellValue != null ? formatter.formatCellValue(cursor) : null);

    isEmpty 는 문자열에 대해서는 정확히 동작한다("0" → false, "" → true). 반면 그리드 행은 AgNumberBoxEditor 로 편집하면 값이 숫자가 될 수 있어, fnSaveValidation 쪽은 지금처럼 ?.toString() 이 반드시 필요하다. 두 함수가 서로 다른 것은 실수가 아니라 입력이 다르기 때문이다.

    화면에서 숨은 file input 을 없앴다 — FileService.select() (PR #268)¶

    협력사 계정(NGB01)이 업무 엑셀을 올리려다 관리자 전용 템플릿 업로드로 빠지는 일이 2026-09-27 ~ 10-12 사이 12회 났다. 운영에 임시 진단을 심어 원인을 규명하고, 구조를 바꿔 같은 일이 생길 수 없게 한다.

    무엇이 문제였나¶

    화면마다 display:none 인 <input type="file"> 을 미리 심어두고 버튼이 $refs.xxx.click() 으로 선택창을 여는 방식이었다. 그 input 이 DOM 에 남아 두 가지를 낳았다.

    1. 밖에서 때릴 수 있다 — el.files 를 꽂고 dispatchEvent(new Event('input')) 을 쏘면 핸들러가 돈다. 버튼을 v-show 로 가려도 input 은 그대로라 소용이 없다
    2. 엉뚱한 input 이 잡힌다 — document.querySelector('input[type=file]') 는 DOM 에서 먼저 나온 것을 집는다. 관리자 전용 input 이 업무용보다 앞에 있던 화면이 넷이었다

    진단으로 받은 값이 정확히 이 모양이었다.

    trusted = false                            ← 선택창을 거치지 않은 합성 input 이벤트
self    = true                             ← 대상이 관리자 전용 uploadFormFile
isAdmin = false, role = ["CRS01"]          ← 버튼 숨김 조건은 정상 동작
file    = SNKO_Estimate.xlsx (4.8~5.6KB)   ← 매일 올리는 업무 엑셀
ua      = Chrome 143 / Windows

    FileService.select()¶

    const file = await FileService.select()      // accept 인자 선택
if ( !file ) return
new FileService( [ file ] ).appendJson( 'param', {...} ).upload()

    DOM 에 붙이지 않은 <input> 을 그 자리에서 만들어 .click() 하고, 선택이 끝나면 버린다. 핸들러는 DOM 리스너가 아니라 클로저라 밖에서 부를 수 없다. 고르는 것과 올리는 것이 한 클래스에 모인다.

    ⚠️브라우저 정책상 사용자 제스처 안에서 호출해야 선택창이 열린다. 버튼 핸들러에서 바로 부르면 되고 await 뒤에서 부르면 막힌다.

    셀 편집 변경 감지: 0 과 빈 값 구분 (사용자 결정 2026-10-08)¶

    이 항목은 화면 동작이 바뀐다. 셀 편집 비교가 newValue || '' 와 oldValue || '' 를 비교해 0 → '', '' → 0, 0 → null, null → 0 이 U 로 잡히지 않았다. 그 행에 다른 변경이 없으면 저장 대상(getItems())에서 빠져, 수량이나 금액을 0 으로 바꾸거나 0 을 지운 수정이 저장된 것처럼 보이고 실제로는 저장되지 않았다.

    • 새 규칙: null, undefined, '' 는 같은 빈 값, 숫자 0 은 따로 구분. 0 이 아닌 값은 종전과 같다(엄격 비교라 0 과 '0' 은 다름, false, NaN 은 빈 값)
    • 이제 잡힘: 0 → '', '' → 0, 0 → null, null → 0, 5 → 0, 0 → 5
    • 계속 안 잡힘: '' → null, null → undefined, undefined → ''(텍스트 편집기가 null 셀을 열었다 닫는 소음, Delete 키로 빈 칸을 지우는 경우)
    • 숫자 편집기 AgNumberBoxEditor: 값이 없는(undefined) 칸을 열었다 그냥 닫기만 해도 0 을 커밋해, 위 규칙에서는 손대지 않은 행이 U 가 됐다. 사용자가 실제로 입력했는지(input 이벤트, 숫자 키로 편집 시작)를 보고, 입력이 없으면 원래 값을 돌려주게 고쳤다(사용자 결정 2026-10-08). 값이 있던 칸을 지우면 0 이 되는 동작은 그대로다.
    • 테스트: components/manual/ag-grid/vue/__tests__/AgNumberBoxEditor.spec.ts(jsdom 에 실물 dx-number-box, 6건). 이를 위해 vitest.config.ts 에 @vitejs/plugin-vue 를 넣어 .vue 를 읽게 했다.

    업로드 화면 7종 — 저장 전 형식·바이트 검사 (공용 ValidateUtil 4종) (PR #238)¶

    • 계기: LCH24(태국 람차방) 견적 엑셀 저장이 ORA-06502 로 실패했다. 1행 EQ_NO 맨 앞에 태국 성조 부호 U+0E49(태국어 자판에서 h 키)가 붙어 있었다. 화면 검사는 .length !== 11 이었는데 .length 는 UTF-16 단위라 이 문자를 1자로 세어 11자리로 통과했다. DB 는 AL32UTF8 에서 3바이트라 13바이트 → VARCHAR2(11 BYTE) 초과. 저장 프로시저가 IN 커서를 임시 테이블 %rowtype 으로 fetch 하므로 칸 하나만 넘쳐도 묶음 전체가 실패한다(같이 보낸 정상 행까지 미저장).
    • 공용 함수(util/premitive/ValidateUtil.ts) — 넷 다 true/false 를 돌려준다. true 면 입력값을 그대로 쓰고 false 면 호출부가 안내한다(여러 행을 모아 창 하나로 보여 주는 화면이 있어 함수 안에서 메시지를 띄우지 않는다).
      • isAlnum(value, length?, mode = 'exact', allow = '') — A-Z a-z 0-9(+allow 문자)만. 빈 값(공백뿐 포함)은 false. 'exact'(기본) 정확히 그 자릿수, 'max' 1 ~ 그 자릿수. ASCII 만 허용하니 글자 수 = 바이트 수라 DB VARCHAR2(n BYTE) 한도와 그대로 맞는다.
      • isDateFormat(value, 8 | 12) — 8 은 yyyymmdd, 12 는 yyyymmddhh24mi. 실제 있는 날짜·시각인지 본다(20260231, 2400, 1260 차단).
      • isNumeric(value) — 십진수(부호, 소수점 허용).
      • isMaxByte(value, maxBytes) — 자유입력 칸(한글 허용)용. UTF-8 바이트가 한도 이하인지(한글·태국어 1자 = 3바이트). 빈 값은 true. 기존 StringUtil.byteLength 는 escape() 기반 어림셈이라 쓰지 않았다.

    • 증상: 협력사 계정이 자기 HALK 견적을 삭제하려는데 You do not have permission. 요청을 보니 ESTIMATE_NO 는 HALK 것인데 COMP_CD 는 SNKO 였다. 서버 소유검증은 정상 동작한 것이고, 프론트가 봉투를 틀리게 실어 보낸 것이다.
